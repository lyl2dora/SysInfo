## K01 首个可运行切片（M1）范围与 P0 模块顺序

- **状态**：已采纳，并按 D14 调整 → **D15**；CPU 模块的具体内容在开工时确认
- **领域**：路线图 · **原分级**：启动前需拍板
- **问题**：M1 先做什么？之后 7 个 P0 模块按什么顺序推进？D06 的合并模式和 D08 的历史持久化插在哪一步？
- **选项**：
  - A：行走骨架 + CPU 占用（只用公开 API），之后按 CPU → 功耗与散热 → 内存 → 网络 → GPU 与加速器 → 存储 → 应用活动推进
  - B：M1 直接做功耗与散热（SMC 私有层），最早拿到差异化能力；但壳和私有桥接同时出问题时难以定位
  - C：先做不带 UI 的采集层 + CLI；27 菜单栏的运行时坑会暴露得很晚
  - D：按尽早替代 Stats 排序：CPU → 内存 → 网络 → 功耗 → 存储 → GPU → 应用活动
- **推荐**：选 A。M1 包含：accessory app 外壳、合并调度 tick、一个固定宽度的自绘 item、面板、CPU 总占用和每簇占用（host_processor_info，拓扑动态发现）、诊断页雏形、自身开销计数。M2 做 SMC 私有层和自检框架。菜单栏达到 3–4 个 item 时实现合并模式。P0 全部做到 L1 之后先做 D08 持久化，再做各模块的 L2 和 P1。
- **理由**：27 菜单栏有几处行为只在真实 app 里才会暴露：session 只认真实点击、autosave 会把新 item 藏掉、实际高度是 30 pt。所以壳层越早验证越好。CPU 占用的数据源最稳定，出了问题容易定位到壳本身。GPU 模块放在引入 IOReportHub 的那一步，要先解决 K06 的预算问题。应用活动跨多个域，放最后返工最少。
- **证据**：调研报告 §3.1 运行时实测（:306-324）、§5.1（:390-402）、§5.2（:404-414）；docs/decisions.md:35-39（D06）、:46-49（D08）、:64-70（D13）；research/probes/cpu/cost.txt（host_processor_info 14.4 µs/次）

## K02 D02 派生标识定稿，以及 Debug 构建是否用独立 Bundle ID

- **状态**：已采纳 → **D16**
- **领域**：工程/构建（标识） · **原分级**：启动前需拍板
- **问题**：D02 写明派生标识「到实现时再最终确认」。建工程时就要定下来：Xcode 跑的 Debug 版和装在 /Applications 的日用版，是共用 zone.lyl.sysinfo，还是给 Debug 加后缀？App Group、widgets、helper 的标识是否照 D02 原样？
- **选项**：
  - Debug 用 zone.lyl.sysinfo.dev（显示名 SysInfo Dev），Release 用 zone.lyl.sysinfo。两版的数据、偏好、TCC 授权和登录项完全隔离，可以同时运行
  - 共用 zone.lyl.sysinfo，Debug 启动时让日用版退出（单实例保护）
  - P0 完成前不装日用版，只跑 Debug（共用 ID），开始日用时再拆分并迁移数据
- **推荐**：选第一项。在 xcconfig 里按 configuration 设置 PRODUCT_BUNDLE_IDENTIFIER；Debug 构建不注册登录项。派生标识按 D02 原样定稿；Debug 版以后如果需要 App Group，就用 D8MFB2YNN3.zone.lyl.sysinfo.dev。两版同时运行时会互相抢 host_statistics 配额，做精度对照前要退出其中一个。
- **理由**：D08 会写盘，schema 也会演进；D11 希望 TCC 授权保持稳定。开发版不能污染日用版的历史数据和 autosave 可见性。Bundle ID 在建工程时就写进配置，事后再改就得迁移数据。
- **证据**：docs/decisions.md:11-16（D02「到实现时再最终确认」）、:46-49（D08）、:57-58（D11）；调研报告 :23（§0-7 配额）、:323（autosave 可见性持久化）

## K04 协作节奏：哪些部分先写设计文档、在哪里停下等你确认、怎样算完成

- **状态**：**用户改定 → D14**：按模块逐个实现，每个模块一次做到完整版。下方「先广后深、先做 L1」的推荐**不采用**

## K06 D12 常驻预算与 IOReport 实测开销冲突：常驻时采什么、历史怎么采

- **状态**：**用户改定 → D19**：菜单栏显示项和采集频率由用户决定，开销由用户承担；D12 的预算只约束出厂默认配置。下方推荐里「菜单栏默认不提供高开销 widget」「放进菜单栏后自动降到 2–5 s」这两条限制**不适用于用户配置**。面板关闭时历史怎么采，在 CPU 模块开工时与 D08 存储一起定（2026-10-15 已定 → D30：background 层继续采样）。D19 只放开本进程开销方面的限制，D09、D10 不受影响
- **领域**：采集层 · **原分级**：启动前需拍板
- **问题**：报告 §5.1 让 IOReportHub 以 1 Hz 的合并订阅常驻，但实测合并采样一次要 8.25 ms CPU（约 0.83% 单核）。单独一个 PMGR 类分组也要 4.2–5.3 ms，超过 D12 规定的常驻 <0.5%，而且减少通道数也降不下来。另外，D08 要求历史持续写盘，D12 要求只在有消费者时才采样。菜单栏和面板都不需要某些指标时，哪些指标常驻采、怎么采？
- **选项**：
  - 严格分档：常驻只用廉价的数据源。簇实际频率、DRAM 带宽、媒体引擎这类 PMGR 指标只在面板打开时订阅，菜单栏不提供这类 widget
  - 默认同第一项，但允许你把高开销指标放进菜单栏：设置里标注「约 +0.5% CPU」，这个订阅自动降到 2–5 s 一次
  - 保持 1 Hz 全量常驻，另加一条决策把常驻预算放宽到约 1%（取代 D12）
- **推荐**：选第二项。常驻的廉价源包括：host_processor_info（14 µs）、sysctl、IFMIB、少量 SMC 键、GPU Stats（0.32 ms），coalition 每分钟扫一次。没有 UI 时历史这样采：累计计数器（CPU tick、IFMIB、磁盘、coalition、PowerTelemetryData）每分钟读首尾两次，差分就得到精确的分钟均值；温度、内存这类瞬时量降到 5–10 s 采一次。GPU 常驻功耗先实测只订阅 AGX「GPU Energy」一个通道的开销，低于 0.5 ms 就用它，否则改用 SMC RP05+RP08。同时补测 SMC 单个键的读取成本。
- **理由**：开销是 PMGR 驱动的固定成本，和通道数无关：18 个通道 4.85 ms，130 个通道 5.05 ms。D12 已经定了，所以优先调整采集策略。需要你确认两点：默认情况下菜单栏看不到实时簇频率；面板关闭期间，历史里的峰值只精确到 5–10 s。
- **证据**：docs/decisions.md:46-49（D08）、:60-62（D12）；调研报告 :54、:168、:170、:395（IOReportHub 1 s，5–8 ms）、:402；research/probes/cpu/cost_merged.txt（8254 µs CPU/次）、cpu/cost.txt、cpu-review/cost_statsset.txt、gap-coalition-attribution/coal_scan.txt（2.82 ms/tick）

## K12 私有符号的声明与链接：统一 C 头文件 + 弱链接，对上按数据源封装成协议

- **状态**：已采纳 → **D23**
- **领域**：采集层（私有 API 隔离层） · **原分级**：按推荐默认
- **问题**：探针里三种做法混用：IOReport 用自写头文件 + -lIOReport 强链接；coalition 和私有 IOHID 用 dlsym；SMC 用公开 IOKit 调用加自定义结构体。产品代码统一成哪种？对业务代码暴露什么接口？

  - 普通 extern 强链接（探针的做法）：任何一个私有符号在系统更新后消失，app 就会在启动时崩溃

## K13 Swift 6 语言模式与采样 actor 的划分

- **状态**：已采纳 → **D23**
- **领域**：工程/构建 · **原分级**：按推荐默认
- **问题**：Xcode 27 模板默认是 Swift 5 模式 + 默认 MainActor 隔离。D03 只要求采样器不能落在主线程，没定语言模式、各 target 的默认隔离，也没定采样用几个 actor。
- **选项**：
  - Swift 6 模式；app target 默认 MainActor，Package 默认 nonisolated；一个 SamplingActor 在每个 tick 里依次跑完所有采集器，慢调用放进独立 actor
  - 保留模板的 Swift 5 模式，采样函数逐个标 @concurrent，漏标一个就会回到主线程
  - Swift 6，每个数据源一个 actor，每个 tick 用 TaskGroup 并行执行
- **推荐**：选第一项。慢调用放进单独的 SlowIO actor 或 @concurrent 函数，包括：启动 nettop 进程（约 20 ms）、读 SMART、CSDiskSpaceGetRecoveryEstimate（15–60 ms）、SMC 全量枚举（1.28 s）。每个 tick 结束后，把结果一次性交给 MainActor 上的 @Observable 存储。@unchecked Sendable 只允许出现在 C 封装层。保留 MemberImportVisibility。
- **理由**：新项目没有历史包袱，Swift 6 能在编译期发现采样落到主线程这类问题。单次采样只要几毫秒，并行节省的时间抵不上多线程唤醒的耗电；串行执行还让 SMC 连接、IOReport 订阅这类有状态的句柄天然互斥。
- **证据**：docs/decisions.md:18-21（D03）；调研报告 :128、:151、:164、:363；research/probes/cpu/cost_merged.txt、gap-coalition-attribution/coal_scan.txt

## K14 私有 API 采集器放在主进程内，不拆成独立的 XPC 服务

- **状态**：已采纳 → **D23**
- **领域**：采集层 · **原分级**：按推荐默认
- **问题**：D05 要求把私有调用集中到一个隔离层，但没说要不要放到单独的进程里。私有函数签名写错，或系统更新改了结构体布局，都会让进程直接崩溃，而启动自检拦不住这类问题。私有采集器是放在主进程里，还是放进 app 内置的非沙盒 XPC 服务（崩溃时只需重启这个服务）？
- **选项**：
  - 放在主进程内（报告 §5.1 就是这样设计的）
  - 所有私有采集器都放进 XPC 服务

## K17 数据模型：按域的值类型、稳定的 MetricID、SI 单位、显式的数据质量状态

## K18 调度：消费者声明需求 + 单个合并 tick，面板内按卡片分配采样

- **状态**：已采纳 → **D24**
- **领域**：采集层 · **原分级**：按推荐默认
- **问题**：菜单栏 item、面板、历史记录器和将来的小组件快照，怎么声明自己需要哪些数据？tick 用哪种定时方式？面板打开时怎样守住 <2% 的预算？
- **选项**：
  - 声明式需求：各消费者注册 Demand(metrics, tier)，释放 token 即注销；只用一个带 leeway 的 DispatchSourceTimer
  - 每个采集器一个 AsyncStream：每条流各自唤醒，很难保证一次唤醒完成全部采样
  - Task + ContinuousClock.sleep 写循环：不能设 leeway，动态改间隔也不直观
- **推荐**：选第一项。Scheduler 把所有需求合并，决定本 tick 要调用哪些采集器；tick 对齐到整秒之后稍晚一点触发，保证 SMC 已经更新。面板内只有可见的 tab 或卡片会注册 1 Hz 的高开销需求；nettop 只在对应卡片可见时每 3 s 调用一次。
- **理由**：合并 tick 的意义就是一次唤醒做完全部采样，leeway 是 macOS 合并定时器唤醒的标准做法。如果面板一打开所有数据源都跑 1 Hz，开销约 3% 单核，超出 D12 的上限。
- **证据**：docs/decisions.md:51-52（D09）、:60-62（D12）；调研报告 :151、:396（SMC 按秒对齐）、:402；research/probes/cpu/cost_merged.txt、gap-coalition-attribution/coal_scan.txt

- **问题**：D05 规定 coalition 自检失败时，回退到同用户的 libproc 加 setuid 的 top。但 top -l 1 每次约耗 150 ms CPU，按 1–2 s 的周期调用会远超 D12 预算。回退具体怎么做？
- **选项**：
  - 只回退到同用户的 libproc；root 和其他用户的进程显示为「不可见（N 个）」
  - 同上，面板打开时每 5–10 s 启动一次 top 补齐（会超过面板打开时 2% 的预算）
  - 同上，另加一个「刷新全部进程」按钮，只在手动点击时启动 top
- **推荐**：选第三项。
