# SysInfo 决策档

> 依据：`docs/research/2026-09-28-capability-sdk-audit.md`（下称「调研报告」）。
> 规则：每条决策带编号、日期和状态（**已定** / **预留**：能力纳入架构、实现排后）。要推翻某条决策时，新增一条并标注「取代 Dxx」，不直接改写旧条目。

## 2026-09-28

### D01 定位 · 已定
SysInfo 是一个从零设计的自用 macOS 菜单栏系统监控 app，**不是** Stats 的移植或 macOS 27 适配。Stats 只作为 popover、菜单栏 widget、桌面小组件的**样式参考**（调研报告 §2）。模块范围和数据源依据本机实测的能力边界来定，不照搬 Stats 的模块划分。

### D02 标识 · 已定
- Bundle ID：`zone.lyl.sysinfo`
- 以下派生标识沿用同一前缀，到实现时再最终确认：
  - App Group：`D8MFB2YNN3.zone.lyl.sysinfo`（必须带 Team ID 前缀，Developer ID 签名下不需要描述文件，见调研报告 §2.3）
  - 小组件扩展（预留，D07）：`zone.lyl.sysinfo.widgets`
  - 特权 helper（预留，D04）：`zone.lyl.sysinfo.helper`

### D03 平台与工程基线 · 已定
- 最低部署版本 macOS 27.0，只支持 Apple 芯片（arm64）；全面采用 Liquid Glass。
- 主 app **不开沙盒**（IOKit/SMC/IOReport/libproc 需要），并关闭 Xcode 27 模板默认打开的 App Sandbox。
- 工具链为 Xcode 27 / Swift 6.4。采样器不能落在主线程：要么是独立 actor，要么用 `@concurrent` 修饰，因为模板默认的隔离是 MainActor。

### D04 风扇控制 · 预留
能力保留、实现排后。
- v1 只读取风扇状态（`F0Ac/F0Mn/F0Mx/F0Tg/F0md`）。
- 架构上预留 SMC 写入的接口抽象，以及特权 helper 的位置：`SMAppService.daemon`、用户在「登录项」中批准、XPC 用 `setCodeSigningRequirement` 锁定 Team ID。
- 这是整个 app 中**唯一**需要 root 的功能。其他所有能力都已找到免 root 的路径（调研报告 §0-3）。

### D05 私有 API 策略 · 已定（按推荐）
自用场景下私有 API 全部可用，范围包括 IOReport、SMC、私有 IOHID、resource coalition、私有 IOPS 等，但要满足以下约束：
- 私有调用集中放在一个隔离层里，业务代码不直接接触。
- 每个数据源启动时自检（例如 coalition 的 slot 11 应等于本进程的 `ri_energy_nj`；SMC 按属性位判断字节序后读到的数值要合理）。
- 自检失败时回退到公开路径（例如同 uid 的 libproc、setuid 的 `top`），或把该指标显示为不可用，不能显示错误的数值。

### D06 菜单栏形态 · 已定
- **默认每个模块一个** status item，并提供「合并为单个 item」的选项。
- 实现方式：自绘 `NSStatusItem.view`，宽度按档固定，数字用等宽字体，颜色用模板/语义色。点击由 `expandedInterfaceDelegate` 驱动，打开 `NSPopover`（链接 27 SDK 时默认就是玻璃效果）或可拖出的 non-activating `NSPanel` + `NSGlassEffectView`。
- 已知风险：模块多时，item 可能被挤进 27 的溢出区，而且 app 收不到任何公开信号。设置里要提示用户切换到合并模式，并说明系统设置「菜单栏 → 允许在菜单栏中显示」的位置。
- 不使用 `MenuBarExtra(isInserted:)`，它在 27.0 上会卡在 100% CPU。

### D07 桌面小组件 / Control · 预留
能力保留、实现排后。
- 架构上预留：采集层输出 Codable 快照，通过 App Group 共享通道（D02）写出。
- 已知约束：扩展必须开沙盒；放置后 30–45 分钟才重载一次，只适合放慢速摘要。

### D08 历史数据 · 已定
- **历史数据写盘持久化**，并**提供导出选项**。
- 做法（按推荐）：内存中保留高分辨率环形缓冲，用于图表；写盘的是分钟级聚合。存储引擎、保留时长和导出格式在设计阶段再定，初步倾向本地 SQLite + CSV/JSON 导出。
- 整机的长期能耗可以直接取 `PowerTelemetryData` 的累加器，它在 app 重启后仍然保留。

### D09 每应用网络流量 · 已定（按推荐）
P1 实现。只在面板打开时调用 `/usr/bin/nettop`（约 20 ms/次），用来覆盖所有用户的进程。统计按流 ID 累计，因为流关闭后进程的累计值会下降。

### D10 Wi-Fi 网络名 · 已定
**不显示** SSID/BSSID，**不申请**定位权限。只显示 RSSI、噪声、速率、信道、PHY 等无需授权的信息。CoreWLAN 只在面板打开时读取，不做轮询。

### D11 签名 · 已定（按推荐）
统一使用 Developer ID Application（Team `D8MFB2YNN3`）签名。这样 TCC 授权能在重新构建后保留，App Group 可以使用，将来的 helper 也能做校验。网络接口计数一律用 IFMIB，不依赖签名类型。

### D12 自身开销预算 · 已定（按推荐）
- 常驻时单核占用低于 0.5%；面板打开时低于 2%。
- 全部采集器共用一个合并的调度 tick，只在有消费者时采样；`systemPrefersReducedResourceUsage` 为真或处于低电量时降频。

### D13 模块范围 · 已定（按推荐，结合 D04/D07）
采纳调研报告 §5.2：
- **P0**：CPU · GPU 与加速器 · 内存 · 存储 · 网络 · 功耗与散热 · 应用活动（跨域的每应用视图）
- **P1**：电源设备（UPS / 配件电量）· 每应用网络流量（D09）
- **P2 / 预留**：风扇控制（D04）· 桌面小组件 / Control（D07）· 阈值提醒
- **不做**：Remote/SaaS、自动更新器、蓝牙扫描模块（由「电源设备」取代）、世界时钟
- 说明：长期历史由 P2 提前为已定能力（D08）。

## 2026-09-28（启动实现）

> 依据：`docs/planning/2026-09-28-kickoff-decision-points.md`（下称「启动清单」，K01–K53），每条的选项、理由和证据都在里面。
> 本节中，K04、K06、K08 由用户改定，对应条目引用了用户原话；其余 K 条目按推荐采纳。几种标记的含义：
> - 「推导」：Claude 根据用户原话补出的配套做法；
> - 「待确认」：到注明的时机要向用户确认；
> - 启动清单里的「待定」项：在各自标注的时机再讨论。

### D14 实现节奏 · 已定（用户改定 K04）
用户原话：「可以按模块实现，每个模块均做完整版。」「模块能力边界可以在各自实现时再讨论。」
- 按模块逐个实现，一个模块做到完整版再开始下一个。完整版包括：
  - 采集器与自检回退、测试；
  - 菜单栏 widget；
  - 该模块适用的完整面板（历史图表、Top N 等）和该模块的设置页；
  - 与系统自带工具的数值对照，以及开销实测。
- 每个模块开工前，先和用户讨论两件事：该模块的能力边界（含 D20 的跨芯片、跨机型差异），以及启动清单中触发时机已到的待定项。定下来再实现。
- 沿用 K04 推荐中用户未改动的部分：
  - 有真实取舍的部分（功耗与散热、应用活动、历史存储、IOReport 调度）先写 `docs/design/<模块>.md`；
  - 每个模块完成后由用户验收；
  - 实现中遇到与决策档冲突的情况或新的真实取舍，先停下来问用户，结论追加为新的 D 条目。

### D15 里程碑顺序 · 已定（按推荐 K01，并按 D14 调整）
- 先做 **M0 骨架**，包括 accessory app 外壳、合并调度 tick、一个固定宽度的自绘 item、统一面板外壳（D21）、设置窗口外壳、诊断页雏形和自身开销计数。骨架只接公开 API 的 CPU 总占用，用来单独验证外壳。
- 之后按模块推进：CPU → 功耗与散热 → 内存 → 网络 → GPU 与加速器 → 存储 → 应用活动。P0 全部完成后再做 P1。
- 待确认（CPU 模块开工时）：
  - 按调研报告，CPU 完整版预计要用到 SMC（温度）、IOReport（实际频率）和 coalition（Top N 进程），所以私有 C 层和自检框架会在 CPU 模块里建立。
  - 完整版包含历史图表，所以 D08 历史存储预计也要在 CPU 模块里定下并实现。涉及启动清单 K33、K34、K39，以及 K06 遗留的「面板关闭时历史怎么采」。
  - 温度归 CPU 还是归「功耗与散热」、历史存储是否并入第一个模块，都属于能力边界，届时由用户确定。
- D06 的「合并为单个 item」在菜单栏同时有 3 个模块时实现。

### D16 标识定稿 · 已定（落实 D02，按推荐 K02、K10）
- Release 用 `zone.lyl.sysinfo`；Debug 用 `zone.lyl.sysinfo.dev`，显示名「SysInfo Dev」。两个版本的偏好、历史库、TCC 授权和登录项互相隔离，可以同时运行；Debug 构建不注册登录项。
- Release 的派生标识按 D02 原样定稿。Debug 版的所有派生标识都放在 `zone.lyl.sysinfo.dev` 之下，例如 `zone.lyl.sysinfo.dev.widgets`、`zone.lyl.sysinfo.dev.helper`，App Group 为 `D8MFB2YNN3.zone.lyl.sysinfo.dev`。
- target 名、模块名和 CFBundleName 统一为 SysInfo。

### D17 Git 流程 · 已定（按推荐 K03）
- `main` 是稳定线。每个里程碑或模块开一个分支（如 `m0-skeleton`、`module/cpu`）。
- 在分支内，Claude 每完成一个能构建的小步就可以自动提交，分支可以推送到远端作备份。模块完成并经用户验收后，再合并回 `main`。
- 远端是 GitHub 私有仓库 `lyl2dora/SysInfo`，不加许可证。提交信息用英文 Conventional Commits。暂不做 CI。

### D18 实现阶段的操作边界 · 已定（按推荐 K05）
- 不用 sudo，不写 SMC。只改本 app 的 defaults 域，开发时只动 Debug 版的 `zone.lyl.sysinfo.dev`。只结束自己派生的测试进程；用户自己运行的程序（包括 Stats）不由 Claude 结束。
- 允许 60 s 以内的 CPU/GPU 限时压测，用来验证功耗和温度读数，每次事先告知用户。
- UI 自查靠截图，需要用户给终端授予「屏幕录制」权限。
- Debug 构建提供一个不经真实点击就能打开面板的入口（如 `--open-panel`），也用来测「面板打开」档的开销。真实点击和键盘导航由用户验收。
- 风扇控制（D04）和修改系统级偏好（如 chronod）都要另行逐次授权。

### D19 显示项与采集频率由用户主导 · 已定（用户改定 K06；取代 D12 第一条，修订 D12 第二条的降频条款）
用户原话：「我认为菜单栏显示项和采集频率应由用户主导，那么用户也应接受开销。」
- 菜单栏显示哪些指标、采集频率多高，都由用户选择。高开销指标也可以放进菜单栏或高频采集，由此产生的本进程开销由用户承担；app 不会因为超出预算而拒绝设置或强行降频。
  - 参考开销：IOReport 单个 PMGR 类分组每次约 4.2–5.3 ms CPU，1 Hz 约 0.5% 单核；调研报告 §5.1 那种四组合并订阅每次约 8.25 ms，1 Hz 约 0.8% 单核。
- D12 的「常驻 <0.5% 单核、面板打开 <2%」改为**出厂默认配置**的设计目标：默认配置必须达标，每个模块完成时按统一口径实测（启动清单 K26）。
- 本条只放开本进程 CPU 开销方面的限制。D09（nettop 只在面板打开时调用）和 D10（CoreWLAN 不轮询）是因为系统级副作用而设的，不受本条影响；要放开它们需要另立 D 条目。
- 频率调节的粒度（全局、逐模块或逐指标）在 M0 实现调度器时和用户确认（启动清单 K45）。无论哪种粒度，都保持单个合并 tick，各间隔取基础 tick 的整数倍。
- 推导：设置里给高开销选项标注大致开销，诊断页显示实测开销，让用户知情后再选择。
- D12 第二条中「全部采集器共用一个合并 tick、只在有消费者时采样」继续有效。「降频」一句由本条修订：触发信号改按启动清单 K20，包括低电量、UPS 放电、锁屏等。待确认（M0 实现调度器时）：自动降频默认开启，用户可以在设置里关闭。

### D20 设备范围：多台 Apple 芯片 Mac · 已定（用户改定 K08，补充 D03）
用户原话：「不止这台M5，还有其他apple slicon mac设备需要使用。」「模块能力边界可以在各自实现时再讨论。」
- 目标设备不只是本机 M5 Pro，还包括用户的其他 Apple 芯片 Mac（机型和系统版本待用户提供）。D03 的最低部署版本是 macOS 27.0；如果其中有不能或不打算升级到 27 的机器，需要重新讨论 D03。
- 推导：所有随芯片或机型变化的东西都不写死，一律在运行时发现或按芯片档案映射。包括核类型与簇拓扑、SMC 键、IOReport 通道名、DVFS 表键、温度与功耗传感器、有无风扇、有无电池。遇到未知芯片或自检失败时按 D05 处理。调研报告只在 Mac17,16 上实测过，其中与芯片相关的结论要在各模块实现时复核。
- 每个模块在不同芯片和机型（台式或笔记本、有无风扇）上的能力边界，在该模块开工时讨论（D14）。待确认（用户给出目标机后）：怎样在目标机上验证。例如由用户在目标机上运行诊断导出并回传结果；无法验证的芯片在模块验收记录里列明。
- 待确认（首次分发到其他 Mac 时）：安装方式，以及是否公证。
  - 经 AirDrop、下载等会带 quarantine 属性的方式传过去时需要公证，公证凭据由用户提供；U 盘、rsync 等方式不一定需要。
  - Makefile 提供可选的 `notarize` 目标；Hardened Runtime 从第一天开启。
  - 仍然不做自动更新器（D13）。
- 如果目标设备包含笔记本：内置电池放在哪个模块、优先级如何，在用户给出机型后讨论。刘海屏的菜单栏更窄，默认启用的模块数按启动清单 K41 考虑。

### D21 面板形态 · 已定（按推荐 K07，细化 D06）
- 采用单个可复用的 non-activating `NSPanel` + `NSGlassEffectView`，做成统一面板，用 tabs 切换模块。点哪个 item 就预选对应的 tab；「应用活动」是其中一个 tab；面板可以拖出来成为浮窗。合并模式下另加一个「总览」tab。
- 不采用 D06 中提到的 `NSPopover` 路线。

### D22 隐私原则 · 已定（按推荐 K21）
- 默认不弹任何授权框，默认没有任何出站连接。需要授权（本地网络、辅助功能、通知）或需要联网的功能，都要用户在设置里手动打开后才申请，并说明用途。设置的「隐私」页列出所有可能的出站目标。
- 不申请蓝牙和定位权限（D10）。不链接 IOBluetooth/CoreBluetooth，也不写蓝牙用途说明。
- 数据来源：
  - 蓝牙配件（如 AirPods）的电量只用私有 IOPS 配件接口（`IOPSCopyPowerSourcesByType`）。
  - UPS 和电池用公开的 IOPS、CoreHID 以及 `AppleSmartBattery`。
- 不调用 `system_profiler`。电源设备的 HID 设备匹配限定在 usage page 0x84（读取元素时用 0x84/0x85），不做宽泛的键盘、指针类 HID 设备匹配，以免触发「输入监控」授权。
- 崩溃和诊断信息只写在本地。

### D23 工程基线 · 已定（按推荐 K09、K11–K15、K22、K23，补充 D03）
- 工程形态：纯 `.xcodeproj`（同步文件夹）加 `Config/*.xcconfig`，Swift 6 语言模式，开启 Hardened Runtime。Debug 和 Release 都用 Developer ID 手动签名（D11）。
- 代码分层放在一个本地 Swift Package 里，分成多个 target：
  - 私有 C 层 `CSysPrivate` → 采集层 → 数据模型（不依赖私有 API）→ 历史存储；
  - 另有 CLI 和测试 target；
  - 业务代码 import 不到 `CSysPrivate`。
- 私有符号统一放在一份 C 头文件里，并用弱链接；对上按数据源封装成带 `selfTest()` 的协议。采集器留在主进程内，不拆 XPC 服务。
- 并发：app target 默认 MainActor，Package 默认 nonisolated。每个 tick 由一个 SamplingActor 串行跑完所有采集器；慢调用放进独立 actor，或用 `@concurrent`。
- 入口用 AppKit `@main` + `LSUIElement`；设置窗口打开期间临时切换为 `.regular`。重新打开 app 时弹出设置窗口，作为兜底入口。
- 默认不引入第三方依赖，确有必要时只用 Apple 官方的 swift-* 包。如果历史存储采用 SQLite（引擎按启动清单 K33 在 CPU 模块开工时定），直接用系统自带的 libsqlite3。
- 开发语言为 zh-Hans，文案统一放进 String Catalog。菜单栏小标签用英文缩写。

## 2026-09-29（M0 验收）

### D26 私有层隔离改为构建期检查 · 已定（取代 D23 中「业务代码 import 不到 `CSysPrivate`」一句）
- M0 实测：Xcode 27 和 SwiftPM 都会把依赖闭包里 C target 的 module map 传给下游，所以就算 `CSysPrivate` 不做成 product，编译器也拦不住 app 或 CLI 去 import 它。
- 隔离改为两层保证：
  - `SysCollectors` 对 `CSysPrivate` 使用 `internal import`；
  - `scripts/check-private-imports.sh` 做构建期检查：先去掉注释和字符串，只要 app 或 CLI 的代码里出现 `CSysPrivate` 就判失败。它由 app target 的第一个构建阶段，以及 `make test`、`make cli`、`make remote-*` 触发，并由 `scripts/test-check-private-imports.sh` 的回归样例（make test 会先跑）保证检查本身有效。
- D05 的其余要求不变：私有调用集中在隔离层，并做自检和回退。

## 2026-10-15（CPU 模块开工前）

### D28 目标设备改为 M5 Pro + M4 Pro · 已定（取代 D25 的设备清单；D25 的其余条款不变）
- 用户把 Mac Studio（M2 Max）换成了 Mac mini，沿用原地址 `user@remote-host`（密钥登录）。现在的目标设备：
  - 开发机：Mac mini Mac17,16，M5 Pro（6 Super + 12 Performance），64 GB，macOS 27.0.1 (26A434)，无电池，接 USB UPS。
  - 对照机：Mac mini Mac16,11，M4 Pro（10 Performance + 4 Efficiency；1 个 E 簇 4 核、2 个 P 簇各 5 核），64 GB，macOS 27.0.1 (26A434)，无电池，已装 Xcode 27.0。
- M2 Max 不再是目标设备。已有的 M2 实测保留在调研材料里，作为跨芯片旁证和合成测试素材，不再作为验收对照。D25 及此前文档中的「Mac Studio」一律读作「远端对照机」。
- 两台仍都是台式机，D20 里与电池、刘海屏相关的条款继续不触发。
- 2026-10-15 在 M4 上做了只读结构比对，结果：
  - 和 M2 一致的部分：核档（P + E）、IOReport 实际频率通道名（ECPM / PCPM / PCPM1）、perf-domains 表键号（1 / 5 / 13）。
  - 和 M2 不同的部分：DVFS 表单位是 kHz，和 M5 一样；有按轨的 `RP*` 功耗键，共 14 个，没有 `PSVR`；`Tp*` 温度键 102 个，另有 `Te*` 10 个，结构和 M2 不同。
  - 这再次说明：系统和 SDK 相同，并不代表数据路径相同，数据路径只能在每颗芯片上实测（D20）。
- 据此，CPU 模块在 M4 上的补测范围是：
  - 温度键归簇与功耗键：重测，包括翻转负载，每段不超过 60 s，事先告知用户；
  - 拓扑与频率：轻量复核精度和真实节奏下的开销；
  - 进程、coalition、Top N：与芯片无关，沿用已有结论。
