# SysInfo 决策档

> 依据：`docs/research/2026-09-28-capability-sdk-audit.md`（下称「调研报告」）。
> 规则：每条决策带编号、日期和状态（**已定** / **预留**：能力纳入架构、实现排后）。要推翻某条决策时，新增一条并标注「取代 Dxx」，不直接改写旧条目。

## 2026-09-28

### D01 定位 · 已定
SysInfo 是一个从零设计的自用 macOS 菜单栏系统监控 app，**不是** Stats 的移植或 macOS 27 适配。Stats 只作为 popover、菜单栏 widget、桌面小组件的**样式参考**（调研报告 §2）。模块范围和数据源依据本机实测的能力边界来定，不照搬 Stats 的模块划分。

### D02 标识 · 已定
- Bundle ID：`zone.lyl.sysinfo`
- 以下派生标识沿用同一前缀，到实现时再最终确认：
  - App Group：`D8MFB2YNN3.zone.lyl.sysinfo`（必须带 Team ID 前缀，Developer ID 签名下不需要描述文件，见调研报告 §2.3）
  - 小组件扩展（预留，D07）：`zone.lyl.sysinfo.widgets`
  - 特权 helper（预留，D04）：`zone.lyl.sysinfo.helper`

### D03 平台与工程基线 · 已定
- 最低部署版本 macOS 27.0，只支持 Apple 芯片（arm64）；全面采用 Liquid Glass。
- 主 app **不开沙盒**（IOKit/SMC/IOReport/libproc 需要），并关闭 Xcode 27 模板默认打开的 App Sandbox。
- 工具链为 Xcode 27 / Swift 6.4。采样器不能落在主线程：要么是独立 actor，要么用 `@concurrent` 修饰，因为模板默认的隔离是 MainActor。

### D04 风扇控制 · 预留
能力保留、实现排后。
- v1 只读取风扇状态（`F0Ac/F0Mn/F0Mx/F0Tg/F0md`）。
- 架构上预留 SMC 写入的接口抽象，以及特权 helper 的位置：`SMAppService.daemon`、用户在「登录项」中批准、XPC 用 `setCodeSigningRequirement` 锁定 Team ID。
- 这是整个 app 中**唯一**需要 root 的功能。其他所有能力都已找到免 root 的路径（调研报告 §0-3）。

### D05 私有 API 策略 · 已定（按推荐）
自用场景下私有 API 全部可用，范围包括 IOReport、SMC、私有 IOHID、resource coalition、私有 IOPS 等，但要满足以下约束：
- 私有调用集中放在一个隔离层里，业务代码不直接接触。
- 每个数据源启动时自检（例如 coalition 的 slot 11 应等于本进程的 `ri_energy_nj`；SMC 按属性位判断字节序后读到的数值要合理）。
- 自检失败时回退到公开路径（例如同 uid 的 libproc、setuid 的 `top`），或把该指标显示为不可用，不能显示错误的数值。

### D06 菜单栏形态 · 已定
- **默认每个模块一个** status item，并提供「合并为单个 item」的选项。
- 实现方式：自绘 `NSStatusItem.view`，宽度按档固定，数字用等宽字体，颜色用模板/语义色。点击由 `expandedInterfaceDelegate` 驱动，打开 `NSPopover`（链接 27 SDK 时默认就是玻璃效果）或可拖出的 non-activating `NSPanel` + `NSGlassEffectView`。
- 已知风险：模块多时，item 可能被挤进 27 的溢出区，而且 app 收不到任何公开信号。设置里要提示用户切换到合并模式，并说明系统设置「菜单栏 → 允许在菜单栏中显示」的位置。
- 不使用 `MenuBarExtra(isInserted:)`，它在 27.0 上会卡在 100% CPU。

### D07 桌面小组件 / Control · 预留
能力保留、实现排后。
- 架构上预留：采集层输出 Codable 快照，通过 App Group 共享通道（D02）写出。
- 已知约束：扩展必须开沙盒；放置后 30–45 分钟才重载一次，只适合放慢速摘要。

### D08 历史数据 · 已定
- **历史数据写盘持久化**，并**提供导出选项**。
- 做法（按推荐）：内存中保留高分辨率环形缓冲，用于图表；写盘的是分钟级聚合。存储引擎、保留时长和导出格式在设计阶段再定，初步倾向本地 SQLite + CSV/JSON 导出。
- 整机的长期能耗可以直接取 `PowerTelemetryData` 的累加器，它在 app 重启后仍然保留。

### D09 每应用网络流量 · 已定（按推荐）
P1 实现。只在面板打开时调用 `/usr/bin/nettop`（约 20 ms/次），用来覆盖所有用户的进程。统计按流 ID 累计，因为流关闭后进程的累计值会下降。

### D10 Wi-Fi 网络名 · 已定
**不显示** SSID/BSSID，**不申请**定位权限。只显示 RSSI、噪声、速率、信道、PHY 等无需授权的信息。CoreWLAN 只在面板打开时读取，不做轮询。

### D11 签名 · 已定（按推荐）
统一使用 Developer ID Application（Team `D8MFB2YNN3`）签名。这样 TCC 授权能在重新构建后保留，App Group 可以使用，将来的 helper 也能做校验。网络接口计数一律用 IFMIB，不依赖签名类型。

### D12 自身开销预算 · 已定（按推荐）
- 常驻时单核占用低于 0.5%；面板打开时低于 2%。
- 全部采集器共用一个合并的调度 tick，只在有消费者时采样；`systemPrefersReducedResourceUsage` 为真或处于低电量时降频。

### D13 模块范围 · 已定（按推荐，结合 D04/D07）
采纳调研报告 §5.2：
- **P0**：CPU · GPU 与加速器 · 内存 · 存储 · 网络 · 功耗与散热 · 应用活动（跨域的每应用视图）
- **P1**：电源设备（UPS / 配件电量）· 每应用网络流量（D09）
- **P2 / 预留**：风扇控制（D04）· 桌面小组件 / Control（D07）· 阈值提醒
- **不做**：Remote/SaaS、自动更新器、蓝牙扫描模块（由「电源设备」取代）、世界时钟
- 说明：长期历史由 P2 提前为已定能力（D08）。

## 2026-09-28（启动实现）

> 依据：`docs/planning/2026-09-28-kickoff-decision-points.md`（下称「启动清单」，K01–K53），每条的选项、理由和证据都在里面。
> 本节中，K04、K06、K08 由用户改定，对应条目引用了用户原话；其余 K 条目按推荐采纳。几种标记的含义：
> - 「推导」：Claude 根据用户原话补出的配套做法；
> - 「待确认」：到注明的时机要向用户确认；
> - 启动清单里的「待定」项：在各自标注的时机再讨论。

### D14 实现节奏 · 已定（用户改定 K04）
用户原话：「可以按模块实现，每个模块均做完整版。」「模块能力边界可以在各自实现时再讨论。」
- 按模块逐个实现，一个模块做到完整版再开始下一个。完整版包括：
  - 采集器与自检回退、测试；
  - 菜单栏 widget；
  - 该模块适用的完整面板（历史图表、Top N 等）和该模块的设置页；
  - 与系统自带工具的数值对照，以及开销实测。
- 每个模块开工前，先和用户讨论两件事：该模块的能力边界（含 D20 的跨芯片、跨机型差异），以及启动清单中触发时机已到的待定项。定下来再实现。
- 沿用 K04 推荐中用户未改动的部分：
  - 有真实取舍的部分（功耗与散热、应用活动、历史存储、IOReport 调度）先写 `docs/design/<模块>.md`；
  - 每个模块完成后由用户验收；
  - 实现中遇到与决策档冲突的情况或新的真实取舍，先停下来问用户，结论追加为新的 D 条目。

### D15 里程碑顺序 · 已定（按推荐 K01，并按 D14 调整）
- 先做 **M0 骨架**，包括 accessory app 外壳、合并调度 tick、一个固定宽度的自绘 item、统一面板外壳（D21）、设置窗口外壳、诊断页雏形和自身开销计数。骨架只接公开 API 的 CPU 总占用，用来单独验证外壳。
- 之后按模块推进：CPU → 功耗与散热 → 内存 → 网络 → GPU 与加速器 → 存储 → 应用活动。P0 全部完成后再做 P1。
- 待确认（CPU 模块开工时）：
  - 按调研报告，CPU 完整版预计要用到 SMC（温度）、IOReport（实际频率）和 coalition（Top N 进程），所以私有 C 层和自检框架会在 CPU 模块里建立。
  - 完整版包含历史图表，所以 D08 历史存储预计也要在 CPU 模块里定下并实现。涉及启动清单 K33、K34、K39，以及 K06 遗留的「面板关闭时历史怎么采」。
  - 温度归 CPU 还是归「功耗与散热」、历史存储是否并入第一个模块，都属于能力边界，届时由用户确定。
- D06 的「合并为单个 item」在菜单栏同时有 3 个模块时实现。

### D16 标识定稿 · 已定（落实 D02，按推荐 K02、K10）
- Release 用 `zone.lyl.sysinfo`；Debug 用 `zone.lyl.sysinfo.dev`，显示名「SysInfo Dev」。两个版本的偏好、历史库、TCC 授权和登录项互相隔离，可以同时运行；Debug 构建不注册登录项。
- Release 的派生标识按 D02 原样定稿。Debug 版的所有派生标识都放在 `zone.lyl.sysinfo.dev` 之下，例如 `zone.lyl.sysinfo.dev.widgets`、`zone.lyl.sysinfo.dev.helper`，App Group 为 `D8MFB2YNN3.zone.lyl.sysinfo.dev`。
- target 名、模块名和 CFBundleName 统一为 SysInfo。

### D17 Git 流程 · 已定（按推荐 K03）
- `main` 是稳定线。每个里程碑或模块开一个分支（如 `m0-skeleton`、`module/cpu`）。
- 在分支内，Claude 每完成一个能构建的小步就可以自动提交，分支可以推送到远端作备份。模块完成并经用户验收后，再合并回 `main`。
- 远端是 GitHub 私有仓库 `lyl2dora/SysInfo`，不加许可证。提交信息用英文 Conventional Commits。暂不做 CI。

### D18 实现阶段的操作边界 · 已定（按推荐 K05）
- 不用 sudo，不写 SMC。只改本 app 的 defaults 域，开发时只动 Debug 版的 `zone.lyl.sysinfo.dev`。只结束自己派生的测试进程；用户自己运行的程序（包括 Stats）不由 Claude 结束。
- 允许 60 s 以内的 CPU/GPU 限时压测，用来验证功耗和温度读数，每次事先告知用户。
- UI 自查靠截图，需要用户给终端授予「屏幕录制」权限。
- Debug 构建提供一个不经真实点击就能打开面板的入口（如 `--open-panel`），也用来测「面板打开」档的开销。真实点击和键盘导航由用户验收。
- 风扇控制（D04）和修改系统级偏好（如 chronod）都要另行逐次授权。

### D19 显示项与采集频率由用户主导 · 已定（用户改定 K06；取代 D12 第一条，修订 D12 第二条的降频条款）
用户原话：「我认为菜单栏显示项和采集频率应由用户主导，那么用户也应接受开销。」
- 菜单栏显示哪些指标、采集频率多高，都由用户选择。高开销指标也可以放进菜单栏或高频采集，由此产生的本进程开销由用户承担；app 不会因为超出预算而拒绝设置或强行降频。
  - 参考开销：IOReport 单个 PMGR 类分组每次约 4.2–5.3 ms CPU，1 Hz 约 0.5% 单核；调研报告 §5.1 那种四组合并订阅每次约 8.25 ms，1 Hz 约 0.8% 单核。
- D12 的「常驻 <0.5% 单核、面板打开 <2%」改为**出厂默认配置**的设计目标：默认配置必须达标，每个模块完成时按统一口径实测（启动清单 K26）。
- 本条只放开本进程 CPU 开销方面的限制。D09（nettop 只在面板打开时调用）和 D10（CoreWLAN 不轮询）是因为系统级副作用而设的，不受本条影响；要放开它们需要另立 D 条目。
- 频率调节的粒度（全局、逐模块或逐指标）在 M0 实现调度器时和用户确认（启动清单 K45）。无论哪种粒度，都保持单个合并 tick，各间隔取基础 tick 的整数倍。
- 推导：设置里给高开销选项标注大致开销，诊断页显示实测开销，让用户知情后再选择。
- D12 第二条中「全部采集器共用一个合并 tick、只在有消费者时采样」继续有效。「降频」一句由本条修订：触发信号改按启动清单 K20，包括低电量、UPS 放电、锁屏等。待确认（M0 实现调度器时）：自动降频默认开启，用户可以在设置里关闭。

### D20 设备范围：多台 Apple 芯片 Mac · 已定（用户改定 K08，补充 D03）
用户原话：「不止这台M5，还有其他apple slicon mac设备需要使用。」「模块能力边界可以在各自实现时再讨论。」
- 目标设备不只是本机 M5 Pro，还包括用户的其他 Apple 芯片 Mac（机型和系统版本待用户提供）。D03 的最低部署版本是 macOS 27.0；如果其中有不能或不打算升级到 27 的机器，需要重新讨论 D03。
- 推导：所有随芯片或机型变化的东西都不写死，一律在运行时发现或按芯片档案映射。包括核类型与簇拓扑、SMC 键、IOReport 通道名、DVFS 表键、温度与功耗传感器、有无风扇、有无电池。遇到未知芯片或自检失败时按 D05 处理。调研报告只在 Mac17,16 上实测过，其中与芯片相关的结论要在各模块实现时复核。
- 每个模块在不同芯片和机型（台式或笔记本、有无风扇）上的能力边界，在该模块开工时讨论（D14）。待确认（用户给出目标机后）：怎样在目标机上验证。例如由用户在目标机上运行诊断导出并回传结果；无法验证的芯片在模块验收记录里列明。
- 待确认（首次分发到其他 Mac 时）：安装方式，以及是否公证。
  - 经 AirDrop、下载等会带 quarantine 属性的方式传过去时需要公证，公证凭据由用户提供；U 盘、rsync 等方式不一定需要。
  - Makefile 提供可选的 `notarize` 目标；Hardened Runtime 从第一天开启。
  - 仍然不做自动更新器（D13）。
- 如果目标设备包含笔记本：内置电池放在哪个模块、优先级如何，在用户给出机型后讨论。刘海屏的菜单栏更窄，默认启用的模块数按启动清单 K41 考虑。

### D21 面板形态 · 已定（按推荐 K07，细化 D06）
- 采用单个可复用的 non-activating `NSPanel` + `NSGlassEffectView`，做成统一面板，用 tabs 切换模块。点哪个 item 就预选对应的 tab；「应用活动」是其中一个 tab；面板可以拖出来成为浮窗。合并模式下另加一个「总览」tab。
- 不采用 D06 中提到的 `NSPopover` 路线。

### D22 隐私原则 · 已定（按推荐 K21）
- 默认不弹任何授权框，默认没有任何出站连接。需要授权（本地网络、辅助功能、通知）或需要联网的功能，都要用户在设置里手动打开后才申请，并说明用途。设置的「隐私」页列出所有可能的出站目标。
- 不申请蓝牙和定位权限（D10）。不链接 IOBluetooth/CoreBluetooth，也不写蓝牙用途说明。
- 数据来源：
  - 蓝牙配件（如 AirPods）的电量只用私有 IOPS 配件接口（`IOPSCopyPowerSourcesByType`）。
  - UPS 和电池用公开的 IOPS、CoreHID 以及 `AppleSmartBattery`。
- 不调用 `system_profiler`。电源设备的 HID 设备匹配限定在 usage page 0x84（读取元素时用 0x84/0x85），不做宽泛的键盘、指针类 HID 设备匹配，以免触发「输入监控」授权。
- 崩溃和诊断信息只写在本地。

### D23 工程基线 · 已定（按推荐 K09、K11–K15、K22、K23，补充 D03）
- 工程形态：纯 `.xcodeproj`（同步文件夹）加 `Config/*.xcconfig`，Swift 6 语言模式，开启 Hardened Runtime。Debug 和 Release 都用 Developer ID 手动签名（D11）。
- 代码分层放在一个本地 Swift Package 里，分成多个 target：
  - 私有 C 层 `CSysPrivate` → 采集层 → 数据模型（不依赖私有 API）→ 历史存储；
  - 另有 CLI 和测试 target；
  - 业务代码 import 不到 `CSysPrivate`。
- 私有符号统一放在一份 C 头文件里，并用弱链接；对上按数据源封装成带 `selfTest()` 的协议。采集器留在主进程内，不拆 XPC 服务。
- 并发：app target 默认 MainActor，Package 默认 nonisolated。每个 tick 由一个 SamplingActor 串行跑完所有采集器；慢调用放进独立 actor，或用 `@concurrent`。
- 入口用 AppKit `@main` + `LSUIElement`；设置窗口打开期间临时切换为 `.regular`。重新打开 app 时弹出设置窗口，作为兜底入口。
- 默认不引入第三方依赖，确有必要时只用 Apple 官方的 swift-* 包。如果历史存储采用 SQLite（引擎按启动清单 K33 在 CPU 模块开工时定），直接用系统自带的 libsqlite3。
- 开发语言为 zh-Hans，文案统一放进 String Catalog。菜单栏小标签用英文缩写。

- 划给「应用活动」：每应用的 GPU、ANE、磁盘、内存、能耗列，以及按应用浏览较长时段。
- 不做：

  - 每核频率、请求频率进主界面（只进诊断页）。

### D30 历史存储 · 已定（C2、C3 按推荐 A；落实 D08、K33、K34、K39、K06 遗留）
- 通用历史库在 CPU 模块里建：
  - 引擎：系统 libsqlite3，WAL + `synchronous=NORMAL` + `auto_vacuum=INCREMENTAL`，用 `user_version` 做迁移。
  - 位置：`~/Library/Application Support/<bundle id>/History.sqlite`，Debug 与 Release 隔离（D16）。
  - 表结构：按 MetricID 存的长表，主键时间在前。与芯片相关的信息（拓扑、机型、系统 build）记在 epoch 表里，变化时新开一段。
- 保留期：
  - 分钟级保留 30 天，包括每分钟 CPU 用量前 10 的应用。
  - 小时级永久保留，只存整机指标。
  - 每应用数据随分钟级一起过期，可以一键清除。
- 写入：内存里按分钟聚合，每 5 分钟一个事务；睡眠、退出、导出前立即提交。
- 面板关闭时由 background 层继续采样，锁屏和显示器睡眠时也不停，不受自动降频影响：
  - coalition 每 10 s；
  - 频率每 60 s；
  - 温度每 10 s；
  - 负载均值、热状态每 60 s；
  - CPU tick：菜单栏 item 开着时复用它的 1 s 样本，否则每 60 s 读一次。
- 面板图表提供 1 时、24 时、7 天跨度。在「历史与导出」页手动导出 CSV（一个文件夹）或 JSON Lines；导出内容不含设备唯一标识。

### D31 Top N · 已定（C5 按推荐 A；落实 K37、K38；修订 D05 的回退示例）
- 分组：
  - 默认按应用分组，一个 coalition 一行，可展开看成员。
  - 终端、Xcode 这类宿主 coalition 保持一行，副标题显示占比最高的成员。
  - 设置里可以切换成「按进程」。
- 结束进程：

  - 不提权（D04）。

### D33 温度键归簇与芯片档案 · 已定（C6 按推荐 C；落实 D20、D24）
- 内置芯片档案，内容全部由实测生成，不按键名推断：键→簇、别名组、三元组变体与代表变体、聚合键、排除键、断电占位值。两台目标机首次启动就能正确显示。
- 运行时继续被动学习并校验：
  - 以每簇功率和 GPU 功率为自变量，按每瓦敏感度判定；GPU 贡献必须小于该簇贡献的 0.65 倍。
  - 与档案冲突时标记出来，并回退到只显示 CPU 最高温。
  - 未知芯片只靠被动学习，收敛前显示「学习中」和 CPU 最高温。
- 诊断页提供「传感器校准」按钮：由用户主动触发约 40–60 s 的翻转负载，结果按「机型 + 系统 build」缓存（D18、D19）。
- 断电占位值一律识别为无读数，显示「—」，数据质量标为不可用，不用 0 或 NaN 代替。M4 实测：`Tp*` 读出 40.0，`Tg*` 读出 −4.0 或 0.0。
- 已知的名字陷阱，都以实测为准：
  - M4 的 `Tp1*` / `Tp2*` 属于 SoC/GPU 区域；
  - M2 的 `Tp1*` 属于第二个 P 簇；
  - M5 的 `Tm1E`、`Tm1I` 属于 M 簇 0，`Tm1p` 不是 CPU 温度。
- E 簇不单列温度行（2026-10-15 用户按推荐确认，讨论稿 §9.3）：面板的「CPU 最高温」只取已归到 P 簇的键；E 簇附近的读数（M4 的 `Te*`、M2 的 `Te04/05/06`）只放在诊断页，标「E 簇附近」，并注明受 GPU 和 P 簇影响大。依据：两台 P + E 芯片上，E 簇满载只升约 2.7 °C，GPU 负载升约 11.5 °C，P 簇满载升约 9 °C。

### D34 D19 参考开销更正 · 已定（修订 D19 的「参考开销」一句）
- D19 引用的 IOReport 开销（每次 4.2–8.25 ms）是紧循环里测的。真实节奏指按 1 s 或更长周期醒来后的第一次调用，CPU 频率订阅在这种情况下每次的开销是：M5 约 9.5 ms，M4 约 8.5 ms，即 1 Hz 约 0.85–0.95% 单核，5 s 约 0.17–0.19%。提高 QoS 也降不下来。
- 建订阅的成本几乎全在 `IOReportCopyChannelsInGroup`：首次约 62–64 ms，之后每次约 28–31 ms。所以通道字典全 app 只枚举一次、共享使用（D29 的 IOReport hub）。

### D35 私有符号改为运行时 dlsym 解析 · 已定（2026-10-15 用户确认；修订 D23 中「统一 C 头文件 + 弱链接」的「弱链接」一词）
- 私有函数一律在运行时用 `dlopen` / `dlsym` 解析，每组用 `pthread_once` 只解析一次，不在链接期依赖私有库：
  - IOReport：`dlopen("/usr/lib/libIOReport.dylib")`；
  - coalition：`dlsym(RTLD_DEFAULT, …)`。
- 理由：弱链接仍要在链接期依赖私有库，Xcode 与 `swift build` 都得加非标准的链接参数；dlsym 不需要任何链接设置。符号缺失时，对应的 `csp_*_available()` 返回 0，app 照常启动，上层回退或显示不可用。这与 D05、D23 的原意一致。
- D23 的其余部分不变：私有声明集中在 `CSysPrivate` 一份头文件里，对上按数据源封装。头文件只暴露 `csp_*` 封装函数，不暴露私有符号本身。
- 「不写 SMC」（D18）由私有层的命令白名单保证：读写共用 selector 2，私有层只定义三个读命令，调用前检查命令字节，并有单测覆盖。
- 详见 `docs/design/cpu-module.md` 偏离记录 2026-10-15 条。

### D36 事实更正：M4 Pro 的两个 P 簇分不出温度归属 · 已定（更正边界稿 §9.3 的归簇结论；D33 的做法不变）
- 2026-10-15 校准实测：M4 Pro 两个 P 簇的温度键在任一 P 簇有负载时都同时上电，对两簇占用差的响应完全一致。边界稿 §9.3「Tp00 一组归 P0、Tp08 一组归 P1」是分析时混用不同滞后造成的假象。
- 功耗轨的归属（§9.2：RP05+RP06 为 P 簇 0，RP00+RP01 为 P 簇 1，RP02 为 E 簇）不受影响，校准复现一致。
- 内置 M4 档案改为两个 P 簇共用同一组温度键。
- D33 的做法不变：档案由实测生成、E 簇不单列温度行、断电占位值识别为无读数。

### D37 校准结果的使用范围与共用温度的显示 · 已定（2026-10-15 用户按推荐确认；修订 D33 中「校准结果按『机型 + 系统 build』缓存」的使用方式）
- 有匹配内置档案的芯片，一律使用内置档案。在这类芯片上做「传感器校准」，只生成核对报告（遗漏、候选、功耗轨），不覆盖内置档案。
- 没有内置档案的芯片，才启用本机校准结果，按「socID + 系统 build」缓存，诊断页标「校准生成，可能偏高」。
- 理由：校准能找回全部核心键（M5 两次、M4 一次实测，召回均为 100%），但会多带进 die/SoC 传感器，簇最高温平均偏高最多约 7 °C。
- 共用温度的显示：几个簇共用同一组温度键时（M4 Pro 的两个 P 簇，D36），温度只显示在档的组标题里（形如「性能核 ×10 · 45% · 62 °C」），簇行的温度格留空。各簇有独立温度键的芯片（如 M5 Pro），照常按簇显示。

### D40 开销预算按「最快档等效时间」考核 · 已定（2026-10-15 用户按推荐确认；修订 D19 的考核口径，预算数值不变）
- 起因：M4 Pro 上，系统把 SysInfo 约 95% 的 CPU 时间调度到能效核（Top N 的 p0 占比 5%）。同样的工作在能效核上花的 CPU 时间约是性能核的 2–3 倍，所以按原始 CPU 时间算，M4 的面板档 3.5%，同样的工作在 M5（没有能效核）上是 2.0%。这是系统为省电做的调度，不该被当成开销变大。
- 新口径：D19 的「常驻 < 0.5%、面板打开 < 2%」按**最快一档（perflevel0）的等效时间**占单核的比例考核：
  - 等效时间 = 在最快档上的时间 + 其他档执行的指令数 ÷ 本进程在最快档上的每秒指令数；
  - 数据取自本进程的 `proc_pid_rusage`（rusage_info_v6：按档的时间、指令数、周期数），是公开接口。
  - 最快档时间太少（< 20 ms）、算不出可靠的每秒指令数时，退回按「周期数 ÷ 最快档顶档频率」估算，结果带 * 注明。这个估算有两个方向相反的偏差（能效核 IPC 较低使它偏高，假设顶档频率使它偏低），只作估算。
- 原始 CPU 时间（`ps -o time=`）、按周期数折算的值、能耗（`ri_energy_nj`，毫瓦）照常记录在 `docs/perf/`，作对照与趋势观察。
- 本条只改考核口径，不改 D19 的预算数值，也不改 D19 中「用户自开的高开销项不受限、设置里标注开销」的规定。

### D42 菜单栏着色即时跟随显示值 · 已定（2026-10-15 用户确认；取代 D32 着色部分的「持续 10 s」与「5 个百分点滞回」，D32 其余不变）
- 起因：验收时用定占用压测加日志追踪核对（87% 和 97% 各 20 s）：widget 显示 86–87% 时，要再等满 10 s 才变橙；显示 97% 后约 8 s 才变红。数值已经过线，颜色却没变，观感上两者冲突。
- 新规则：菜单栏着色只是数值的另一种表达，不额外带时间语义。
  - 判定值就是 widget 显示的那个整数（τ = 1.5 s 平滑后四舍五入的值）：显示 ≥85% 橙，≥95% 红，低于阈值立即恢复。

### D45 CPU 功耗不校准；30 分钟批次的展示 · 已定（PT2、PT3 按推荐 A；关闭 K35、K36）

### D46 长期能耗改为 PDTR 积分 · 已定（PT5 按推荐 A；修订 D08 最后一句）

  - 本 app 对 `PDTR` 按实际间隔做 1 Hz 积分（单样本最多覆盖 1.05 s，不外推睡眠和间隙），按分钟写入历史库，小时级永久保留，面板换算成按天的 kWh。
  - app 没运行的时段，用累加器差值补上，标「系统累计，可能偏低」。
  - 累加器每 60 s 与 PDTR 积分对账，结果进诊断页，丢失的分钟标出；连续失配时把补数标为可疑。
- 因此 PDTR 在后台按 1 s 采样，不受自动降频影响（同 D30 的 background 层）；开销为每秒一个 SMC 键，约几十微秒。
- 墙插功率只在面板概览的次要位置显示，标「估算」，不提供菜单栏 widget。

### D48 日用版全局单实例 · 已定（2026-10-16 用户按推荐确认 S1 = A、S2 = A；补充 D16）
- 起因：此前没有任何单实例保护。LaunchServices 只按路径去重，`/Applications` 与 `build/` 下的两份副本、`open -n`、直接执行二进制都能跑出第二个实例；两个实例会同写一个历史库（`sample_minute` 主键冲突、能耗积分重复），菜单栏也会出现两套 widget。

### D49 内存模块的能力边界与出厂默认 · 已定（M1–M6 按推荐；落实 D29 的划分、K40 中本模块部分）

- 不做：jetsam 优先级与内存上限（需要 root 或 entitlement）；spawn `top`、`vm_stat`、`memory_pressure`；单独列出 purgeable；按数值着色。

### D54 存储模块的能力边界与出厂默认 · 已定（2026-10-16 用户改定显示范围、widget 默认与面板分组，其余按推荐；修订 D38、D51）
- **只显示物理盘**：内置盘和外置物理盘（含 RAID 成员）。磁盘映像、模拟器卷、synthesized APFS 容器、RAID 虚拟盘等非物理盘一律不作为「盘」出现。
- **以盘为单位，不以阵列为单位**：SMART、温度、读写速率都按物理盘读取和显示。RAID 不合计读写，否则数据失真。容量和阵列状态（Online/Degraded、各成员状态，读 IORegistry `AppleRAID-*`，不 spawn `diskutil`）本来就是阵列或容器的属性，所以挂在分组标题上，不拆到成员盘。
- **SMART 全量**：每块 NVMe 盘显示健康日志中能读到的全部字段。内置 Apple 盘的通电时间照常显示，但标注「控制器低报，不可信」（取代调研报告「内置盘隐藏此项」的建议）。只读日志页，不发自检等任何会改变设备状态的命令；ATA/USB 盘不开启 ATA SMART（开启要写设备状态），显示「不可用」。SMART 读取频率在实测开销及其对外置盘低功耗状态的影响后再定，结论另记 D 条目。
- **面板（两级）**：
  - 概览页按「内置 / RAID（如有）/ 外置」分组，RAID 默认展开，展开状态会记住。每块盘两行：名称、温度、已用寿命（有异常时换成异常项）；读写速率与短曲线。下面是按磁盘 IO 的 Top N（coalition，照 D31，只在面板可见时采样）。
  - 点击某块盘，面板原地切换到单盘详情页（读写历史图 + 全部 SMART 分组），左上角返回。切换方式同 D47，不先隐藏再显示。
  - 盘太多超出屏幕时，只让盘列表在限定高度内滚动。
- **菜单栏 widget**：
  - 盘温：默认内置盘，可选任意一块盘或「所有盘最高温」。**出厂默认打开**（修订 D51：出厂默认 widget 变为 4 个）。
  - 读写速率：照 Stats 的做法，一个 widget 上下两行显示 R 和 W，作为 D38「一个 widget 一项」的例外（读写算同一项「吞吐」）。绑定一块物理盘，默认内置盘。出厂默认关。
  - 其余候选（可用容量等）在设计文档中定，出厂默认关。
- **不做**：弹出 / 卸载等任何改变卷状态的操作；SSD 节流（IOReport `BW Scale Factor`）只进诊断页；每应用的磁盘 IO 历史划给应用活动。
- **历史**：读写按分钟差分；容量按小时；SMART 每天一份快照，用于看写入量和磨损趋势。历史库中盘的标识用本地加盐哈希，不存序列号；导出只写「型号 + 位置」。
- 跨机说明：对照机 M4 只有内置盘，外置盘、RAID、雷电 SMART 只能在 M5 上验收，验收记录里写明（D20）。

### D55 SMART 读取频率与焦点盘 · 已定（2026-10-16 按实测定，用户授权「没提到的按默认」；落实 D54 的待定项）
- 实测（`docs/design/storage.md` §1）：plugin 常驻时单盘一次 SMART 约 0.13–0.18 ms CPU（M5、M4）；每次重建 plugin 约 0.7–1.0 ms。外置 Intel 盘不支持自主电源切换，内置盘只有 OFF/ACTIVE；60 s 内每秒读全部盘与不读相比，NVMe 电源状态驻留都是 100% ACTIVE，轮询不影响盘的低功耗。
- 做法：
  - plugin 常驻，盘消失或自检时释放。
  - 盘温 widget 按存储模块的常驻间隔（跟随全局，默认 1 s）读，但只读它绑定的盘（「所有盘最高温」时读全部盘）；其余盘最多每 60 s 读一次给历史。
  - 面板存储 tab 可见、诊断页打开时每 2 s 读全部盘（可设 1 / 2 / 5 s）。
- 出厂另加「可用空间」widget（默认关），绑定一个容量组。

## 2026-10-16（存储模块实现中）

### D56 SMART 连接不常驻 · 已定（2026-10-16 按实测修订，待用户验收时确认；修订 D55 中「plugin 常驻」一条）
- 实测：NVMe SMART 的用户态连接是**独占**的。SysInfo Dev 常驻连接期间，另一个进程打开同一块盘返回 `kIOReturnExclusiveAccess`（0xE00002BE）。常驻会让 Stats、smartctl 等其他读 SMART 的程序，以及同时运行的另一个 SysInfo（D16：Debug 与 Release 可以同时运行）都读不到。
- 做法：每次读取都「打开 → 读 → 关闭」，连接只存在约 1 ms；Identify Controller 按盘缓存，只读一次。单盘一次约 0.7–1.0 ms CPU（常驻时约 0.17 ms）。
- 被别的程序占用时，这一轮跳过该盘、保留上一次读数；连续 3 轮被占用才标为不可用；诊断页显示「被其他程序占用」。
- D55 的其余部分不变：盘温 widget 只读绑定的盘，面板与诊断页 2 s 读全部盘，其余盘每分钟一次给历史。开销按新单价：出厂默认（盘温 widget 绑内置盘，1 s）约 0.08% 单核；面板打开时 6 块盘每 2 s 约 0.25% 单核。

### D58 ANE 准实时功率估算上线 · 已定（G5 = A；关闭 K36 遗留项，补充 D45）

### D60 网络模块的能力边界与出厂默认 · 已定（N1、N2、N5–N9 按推荐 A；落实 K40 中本模块部分，修订 D51）
- **主接口**（N1）：默认路由所在的接口（SCDynamicStore `State:/Network/Global/IPv4` 的 `PrimaryInterface`，没有 IPv4 时看 IPv6），收到变更通知时更新，不轮询。默认路由是隧道（utun / ipsec / ppp）时，改用隧道下面的物理接口：`Setup:/Network/Global/IPv4` 的 `ServiceOrder` 中第一个有 IPv4 状态、且接口不是隧道的服务。面板标「VPN」；判定依据是 `PrimaryService` 带 `VPN` 子键，或 `PrimaryInterface` 是隧道，不靠「utun 有地址」。依据：代理软件 TUN 下 utun 只计隧道内层，经系统代理的流量不经过 utun，en0 才是线上真实流量。
- **显示哪些接口**（N1）：面板列出活跃的物理接口，条件是有 IOKit 背后的控制器、不是 `IOUserEthernet` / `AppleUSBDeviceNCM`、且链路 active 或有地址。Thunderbolt Bridge 以 bridge0 一行出现，成员端口不单列。虚拟接口（utun、vmenet、虚拟机 bridge、awdl、llw）折叠成一组，可以展开。分类在运行时按控制器和 SC 类型判断，不按接口名或驱动类名写死。
- **不把全部接口相加**：虚拟机、VPN 流量会在多个接口上重复计数（实测代理软件 TUN 下合计约为真实的 2 倍）。允许的合计只有「物理接口合计」。
- **字节口径**：显示的是接口字节（含协议头），不是应用载荷。计数只用 IFMIB（CLAUDE.md）；负差值按复位处理，睡眠后第一个差分丢弃，接口 index 变化时重建基线。
- **菜单栏**（N2）：
  - 「网速」widget 上下两行显示 ↑ / ↓，作为 D38「一个 widget 一项」的例外，同存储读写速率。可绑定「主接口（自动跟随）」（默认）、某个接口或「物理接口合计」。单位默认字节 / 秒，可改成比特 / 秒。**出厂打开**（修订 D51：出厂默认 widget 变为 5 个），常驻约 0.01% 单核。
  - 「延迟」widget 只在 D61 的延迟功能开启后可选，出厂关。
- **Wi-Fi**（N5，落实 D10）：只在面板里 Wi-Fi 卡片可见时读 CoreWLAN，每 5 s 一次，面板关闭就停；D10 的「不轮询」指后台不读。显示 RSSI、噪声、SNR、发送速率、信道 / 频段 / 带宽、PHY。不显示发送功率（M4 读出 1496 mW）。Wi-Fi 的链路速率用 CoreWLAN 发送速率（IOKit `IOLinkSpeed` 对 Wi-Fi 恒为 0）。
- **每应用流量**（N6）：维持 D09，留到 P1，网络面板这次不放 Top N。实测 `nettop -L 1` 单次 44–67 ms CPU、墙钟 5–30 s，单次调用的路线不可用；P1 开工时改测常驻流式模式，与 K49 一起定。
- **历史**（N7）：每个活跃物理接口和主接口按分钟记入 / 出字节（规则同上），按现有规则汇总成小时。面板显示「今日 / 本月」流量，默认按主接口，可切换接口。面板关闭时 background 层每 60 s 读一次全部接口。延迟开启时，RTT 与丢包也按分钟记。
- **面板**（N8）：概览（主接口类型、名称、链路速率、VPN 标记，实时 ↑↓ 曲线，今日 / 本月流量）；接口列表；连接信息（本机 IPv4 / IPv6、网关、DNS 取 Global 键、代理是否开启，地址可点击复制，全部由变更通知驱动）；Wi-Fi 卡片；延迟卡片（D61）；公网 IP 按钮（D62）。
- **只放诊断页**（N9）：全部接口的原始 IFMIB（包数、错误、丢包、组播、冲突；`IOUserEthernet` 的丢包标「不可靠」），接口分类依据，链路速率来源，SCDynamicStore 原始键，NWPath 的 `linkQuality` / expensive / constrained，CoreWLAN 原值。
- **数据源全部公开**：IFMIB sysctl、IOKit 网络属性、SystemConfiguration、CoreWLAN、ICMP DGRAM socket。不需要私有层；不用 `SIOCGIFLINKPARAMS`（不在公开头文件里），以太网链路速率用 IOKit `IOLinkSpeed`（约 1.9 ms/次，只在链路变化或面板打开时读，缓存）。
- **不做**：SSID / BSSID、定位权限、Wi-Fi 扫描（D10、D22）；局域网设备发现与 Bonjour；测速；逐连接列表；任何改变网络设置的操作。
- 跨机说明：两台都是有线 10 GbE 为主、Wi-Fi 同时在线的台式机；笔记本、USB / 雷电以太网转接器、启用中的 Thunderbolt Bridge、系统 VPN（IKEv2 / WireGuard）都没测，验收记录里写明（D20）。

### D61 网络延迟 · 已定（N3 = A；关闭 K47）
- 实测（`docs/design/network.md` §1.5）：在 Developer ID 签名、独立启动的 .app 里，ICMP **受本地网络隐私约束**。发往默认网关和非直连网段放行、不弹窗；发往同网段其他设备返回 `EHOSTUNREACH` 并弹授权框。用户所在的两个网络里，`1.1.1.1` / `8.8.8.8` 被本地设备代答（0.5–0.9 ms、TTL 62），测不到外网；`223.5.5.5` 是真实的（20–26 ms）。
- 做法：
  - **默认关**（D22：默认没有出站连接）。在设置里开启时选择目标：「默认网关」（无需授权，只反映局域网）和 / 或「自定义公网地址」（默认填 `223.5.5.5`，旁边说明常见公网地址可能被代答），两者可同时开。不提供同网段其他设备（需要本地网络授权）。
  - 只在网络面板可见或延迟 widget 打开时发包，间隔不少于 2 s，默认 5 s。显示 RTT 与丢包率；IPv6 回包按 type 和 id 过滤。
  - 设置的「隐私」页列出这个出站目标。

### D62 公网 IP · 已定（N4 = A；关闭 K48）
- 面板里放「查询公网 IP」按钮，点一次发一次 HTTPS 请求，结果只显示、不进历史，不做归属地。
- 查询服务地址是设置项，默认留空，第一次点击时请用户填写或从候选里选。设置的「隐私」页列出它。
- 不自动查询（D22；本机的代理开关会改变结果，自动查询容易误导）。

### D63 长清单的子面板样式交给合并模式；合并模式排在应用活动之前 · 已定（2026-10-17 用户决定；落实 D50 的时机，新增 K54）

## 2026-10-17（合并模式验收：面板高度）

### D66 面板高度：换页不加动画、一次换完；面板设高度上限，内容区超出时滚动 · 已定（2026-10-17 用户按推荐确认；取代 D64 §7.1 中「改高时加一段短过渡（约 0.15 s）」，补充 D47、D64）
- 起因：验收时用户指出，合并模式下用切换器换 tab 时，切到较高的页会出现「自上往下展开」的动画，切到较矮的页（存储）则不会，效果不统一；功耗页在合并模式下高 983 pt，超出 1080p 屏幕（程序坞在下）的可用高度约 32 pt，面板被推到菜单栏上。
- 原因：新内容先按旧高度绘制（顶部对齐，下半截被截掉），下一轮再用动画改高；`anchoredFrame` 只钳面板底边、不限制高度，超高时整块上推；主页没有高度上限（D64 只给二级页加了限高滚动）。
- 做法：
  - **换页不加动画**：切换器、⌘1–⌘7、总览卡片、二级页的推入与返回、Esc、再次点击 widget，都先在同一轮里量好新内容的高度，再在同一次提交里换内容、改窗口大小（同 D47 的原地切换）。模块内部的结构变化（展开详情、卡片出现、行数变化）同样直接改高，不加动画。
  - **面板高度上限**：锚定时面板顶边固定在菜单栏下方 6 pt，任何情况下都不再上推；最大高度 = 从这里到屏幕可用区域底边减 8 pt。浮窗的上限是可用区域高度减上下边距。
  - **内容区滚动**：顶栏与切换器固定；下面的内容区统一放进一个只在超高时可滚动的区域。二级页原来各自的限高滚动并入这一处，全面板只有一套机制。换页时滚动位置回到顶部。
- 与 D64「主页定高」不冲突：定高是设计目标（主页高度不随实体数量增长），上限是按屏幕兜底（屏幕矮、程序坞大、合并模式多一行切换器）。
