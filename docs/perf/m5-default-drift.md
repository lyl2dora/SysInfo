# M5 出厂默认档考核值在 0.2% 附近波动的原因（2026-10-19）

> 起因：做 P1 电源设备模块时与 main 交替测出厂默认档（`docs/perf/power-devices.md` 末尾），main 四次为 0.167% / 0.188% / 0.233% / 0.232%，平均 0.205%，而 10-18 的 1.0.0 记录是 0.172%（`docs/perf/release-1.0.0.md`）。M4 同档约 0.10%。本记录只查原因，不改口径、不改实现。

## 结论

1. **漂移几乎全部来自分母**（`sysinfo-cli ipsref` 参照值），不是 app 的工作量在变。
2. 参照值短时间内很稳（同一时段连测十几次，离散 < 1%），但**不同时段之间**能差 30% 以上（8.0–11.7 G/s）。原因是 ipsref 的负载以内核调用为主（约 88% 时间在内核），每条指令的耗时随整机的后台负载变化；它测到的是「此刻的最快核」，不是 D80 想要的「满频最快核」。
3. app 的总指令数（分子）本身也在 17.9–20.6 M/s 之间，并且比 M4 高约 28%，这部分与本机进程数有关（见「分子」一节）。
4. 用 10-18 的参照值 11.70 G/s 换算，10-19 的全部九次结果都在 0.153–0.176%；用今天平静时段的 10.1 G/s 换算，平均 0.194%、最高 0.204%。也就是说：**app 没有变重，但在本机当前的日常负载下，出厂默认档离 0.2% 只剩约 3% 的余量**，考核结果是否超预算主要取决于测量当时机器忙不忙。

## 数据

### 1. 分子与分母的离散度（已有九次 M5 出厂默认档）

来源：`release-1.0.0.md`（10-18 一次）与 `power-devices.md` 末尾（10-19 main 四次、p1/power-devices 四次）。main 第一次没写参照值，按 17.9 ÷ 0.167% 反推为 10.72。

| 量 | 平均 | 变异系数 | 范围 |
|---|---|---|---|
| app 总指令（M/s） | 19.6 | 5.0% | 17.9–20.6 |
| 参照值（G/s） | 9.88 | 12.0% | 8.03–11.70 |
| 考核值（%） | 0.201 | 14.5% | 0.167–0.242 |

- 考核值与 1/参照值 的相关系数 0.95，与总指令的相关系数 0.58。
- 10-19 的七次按时间排列，参照值从 16:30 的 10.63 一路降到 16:46 的 8.03（10.63、10.82、9.77、8.84、9.66、8.77、8.03），与分支无关；同一时段 app 总指令没有同样的趋势。

### 2. 参照值短时稳定性（临时 launchd 任务，2026-10-19 17:03–17:09，用户同意）

Claude 会话内 `ipsref` 的 coalition 自检不过（自身 coalition 80 个成员），所以把 Release 构建的 `sysinfo-cli` 和一个诊断探针放到 `/private/tmp` 下由 `launchctl submit` 运行，12 轮、每轮 ipsref 10 s + 探针两种负载各 10 s，跑完即 `launchctl remove`。不启动 app。

探针（不进库）在 userInteractive 线程上连续跑一种负载，读 `rusage_info_v6` 的最快档指令、周期与用户态/内核态时间：
- compute：纯用户态整数运算（xorshift 依赖链），几乎不进内核；
- procscan：`proc_listallpids` + 逐个 `proc_pidinfo(PROC_PIDTASKINFO)`，与 ipsref 的主体（Top N 扫描）同类。

| 负载 | 最快档每秒指令（G） | 变异系数 | 最快档频率（GHz） | 内核时间占比 |
|---|---|---|---|---|
| ipsref | 9.98–10.21（平均 10.14） | 0.7% | — | — |
| compute | 8.63–8.89 | 1.0% | 4.39–4.53 | 0.3% |
| procscan | 11.72–12.94 | 2.6% | 4.30–4.41 | 87–89% |

同一时段负载平均 4.4–6.5、1100 个左右进程，WindowServer 13–25%；后台常驻一个远程桌面进程（约 85%）和一个虚拟机（约 10–50%）。频率稳定在 4.3–4.5 GHz，没有热降频迹象（`pmset -g therm` 无记录）。

### 3. 构建之后马上测是否偏低（会话内，探针 procscan）

`make measure` 先构建 Release app 与 cli，紧接着测参照值。为确认构建后的后台活动（索引、签名扫描等）是否拖低参照值：构建前 procscan 12.56–12.59 G/s；Release 构建（60 s）完成后连测 16 次，12.18–12.66 G/s，只有一次掉到 11.26（同时远程桌面进程冲高）。构建后约低 2%，不是主因。

### 4. 两台机器对比

| | M5 Pro（本机） | M4 Pro（对照机） |
|---|---|---|
| compute（G/s） | 8.6–8.9 | 8.86–8.89 |
| procscan（G/s） | 11.7–12.9 | 19.7–20.1 |
| procscan 每周期指令 | 约 2.9 | 约 4.7 |
| ipsref（G/s） | 8.0–11.7（不同时段） | 15.30–15.33（连测三次；10-18 为 15.54） |
| 进程数 / 负载平均 | 约 1100 / 4–8 | 约 865 / 1.2–1.3 |

纯用户态负载两台几乎一样，差别全在内核路径：对照机几乎空闲，同样的 `proc_pidinfo` 循环每周期能多做 60% 的指令。M5 上 ipsref 比 M4 低三分之一，并不是 M5 的核更慢，而是本机日常后台更忙（远程桌面、虚拟机、多个 Claude 会话与构建）。

## 分子：app 的总指令

- 九次在 17.9–20.6 M/s，变异系数 5%，没有随时间或分支变化的趋势；两组交替测量里各自的第一次偏低（17.9、18.1）。
- 出厂默认档面板关闭时的后台工作（按代码梳理，未逐项计时）：
  - 每秒：CPU 占用（`host_processor_info`）、整机功率（SMC `PDTR`，外加读一次 IORegistry 的电源遥测字典）、内存（sysctl）、主盘温度（NVMe SMART，每次打开、关闭一次库）、网速（IFMIB）、能耗历史；
  - 每 10 s：传感器、GPU 功率与温度、加速器，以及应用活动的 coalition 扫描（`proc_listcoalitions` + 每个 coalition 一次 `coalition_info`，之后对全部 coalition 做差值、排序和身份挑选）；
  - 每 60 s：CPU 频率、PMGR 批次、存储 IO 与容量等。
  - 面板关闭时不跑 Top N、不扫 `proc_pidinfo`。
- 只有 coalition 扫描随机器上的进程规模变化，但两台机器的 coalition 数相近（M5 891、M4 817，`selftest`），而且它 10 s 才一次，解释不了 M5 比 M4 多出的约 28%（19.6 对 15.3 M/s）。这部分差别更可能来自每秒项在两台机器上的路径差异（如 SMART 读的是哪块盘、电源遥测字典的大小），本次没有在 launchd 下对 app 做 `sample` 逐项拆分。
- 分子没有在变，所以这次不需要为它做优化。若以后想多留余量，不改变显示的可选项有：coalition 的足迹数组改为按需排序、身份挑选改为 top-K、跳过全零差值（都在 10 s 节奏上，收益有限）；收益较大的是把菜单栏盘温的 SMART 读从 1 s 放宽到约 5 s，但这会改变盘温的刷新频率，属于功能取舍，需要用户决定。

## 建议

1. **app 侧不需要处理。** 工作量稳定，按平静时段的参照值仍在预算内；10-19 的「0.23%」是参照值被当时的后台负载压低造成的。
2. **考核口径值得修一下，需要用户拍板（会改 D80 的「参照值每次现测」，要追加 D 条目）。** 可选做法：
   - A（推荐）：ipsref 改为连测 3 次、每次约 5 s，取最大值；同时输出最快档频率与每周期指令，频率明显低于 DVFS 顶档或三次相差超过 5% 时提示「参照值受干扰」。取最大值更接近 D80 字面上的「满频最快核」，仍然每次现测，不写死芯片数值。
   - B：每台机器在平静时测一次参照值，存进不进库的本地文件（如 `Config/ipsref.local`），考核都用它，系统 build 号变化时重测。最稳，但偏离「每次现测」，且「平静」本身难界定。
   - C：口径不变，只规定 M5 出厂默认档要取三次以上的中位数再判定。最省事，但解决不了 M5 与 M4 参照值因后台差异而不可比的问题。
3. 无论选哪种，`make measure` 前最好先看一眼后台：本机常驻的远程桌面进程（约 85%）和虚拟机会同时抬高 WindowServer 与压低参照值。
