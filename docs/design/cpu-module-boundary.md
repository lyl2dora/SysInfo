## 1. 目的与口径

按 D14，CPU 模块开工前要先和你定下这个模块的能力边界，同时处理启动清单里触发时机已到的待定项：K06 遗留的「面板关闭时历史怎么采」、K33、K34、K37、K38、K39、K40、K42。本文是这次讨论的材料，依据是 2026-09-29 在两台目标机上的实测：

- 本机 Mac mini：Mac17,16，M5 Pro（perflevel0「Super」6 核 cpu12–17；perflevel1「Performance」12 核两簇 cpu0–11），macOS 27.0（26A428）。
- Mac Studio：Mac14,13，M2 Max（8 Performance + 4 Efficiency），调研中途自动更新到 macOS 27.0.1（26A434），见 §3.1。

调研分四个视角：拓扑与频率、温度与功耗、进程与 Top N、产品方案。前三个硬件视角各有一个独立复核者，用不同的方法和参照物重测。**复核推翻或部分推翻的结论，本文一律以复核后的结论为准，并标「复核修正」**；两方仍有分歧的地方写明分歧。汇总时抽查了几处关键证据（M2 的 coalition 自检输出、参考实现缺少交叉核对、真实节奏下的 IOReport 开销），没有重跑探针。

口径：
- 「M5」指本机 M5 Pro，「M2」指 Mac Studio 的 M2 Max。M2 的数据除注明外都是在 26A434 上测的。
- 开销一律指本进程的线程 CPU 时间；「% 单核」= CPU 时间 / 墙钟。「真实节奏」指按 1 s 或更长周期醒来后第一次调用的开销。紧循环测到的数字会偏低 1.5–2.5 倍，不能用来估常驻开销（§3.2）。
- 两台机器上都有其他调研 agent 同时在跑负载。开销取多次中位数，噪声在对应条目里注明。所有负载测试每次都不超过 60 s。

## 2. 两台机器的能力矩阵

「私有」一列：「是」表示用私有符号或私有接口；「否（未文档键）」表示用公开 API 读未文档化的属性。

### 2.1 拓扑与占用

| 指标 | 推荐来源 | M5 | M2 | 开销 | 私有 | 发现方法 |
|---|---|---|---|---|---|---|
| cpu 编号 → 簇 | `IODeviceTree:/cpus` 子节点的 `logical-cpu-id`、`cluster-id`、`die-id` | 可用：18 核 3 簇，cpu0–5 / 6–11 / 12–17 | 可用：12 核 3 簇，cpu0–3（E）/ 4–7 / 8–11 | 启动一次，含 sysctl 共 0.35 / 0.40 ms | 否（未文档键） | 簇键取 (die-id, cluster-id)；DT、`hw.logicalcpu_max`、`host_processor_info`、IOReport 逐核通道四处核数交叉校验 |
| 簇 → 核档（perflevel）与档名 | `hw.nperflevels`、`hw.perflevelN.{name,logicalcpu_max,cpusperl2}`；档次用三种依据判定：核数、DVFS 表顶频率、DT `l2-cache-size` 的大小顺序 | 可用：perflevel0「Super」= 簇2（表顶 4608 MHz）；perflevel1「Performance」= 簇0+簇1（4380 MHz） | 可用：perflevel0「Performance」= 簇1+簇2（3504 MHz）；perflevel1「Efficiency」= 簇0（2424 MHz） | 启动一次；频率依据要读 pmgr（1.8 / 3.3 ms）和 IOReport 结构 | 频率依据要用私有 IOReport，其余公开 | 三种依据都求、交叉核对，冲突时标 degraded，只给每簇数据（§7.1） |
| 每核占用（user/system/idle/nice） | `host_processor_info(PROCESSOR_CPU_LOAD_INFO)`，M0 已在用 | 可用：20 Hz 连续调用无陈旧 | 可用：与 IOReport 逐核活跃驻留相差 0.0–0.9 pp | 5–17 µs/次 | 否 | 下标即 logical cpu（两台都实测） |
| 每簇 / 每档 / 总占用 | 每核 tick 差分按拓扑求和 | 可用 | 可用 | <1 µs | 否 | 档次判定不成立时只给每簇 |

- 复核确认：两台的核号映射都用「线程落点 + 每核 tick + 逐核通道活跃%」三方对照过，相关系数 ≥0.998。
- 复核确认：映射也和内核自己的按档计数对上了。本进程 `ri_*_ptime`（公开的 rusage v6）和私有 `PROC_PIDTHREADCOUNTS` 给出的按档时间占比，与按我方映射算出的占比吻合，例如 M2 全核 69.8% 对 68.9%，M5 单个 UI 线程 98.5% 对 98.4%。
- 复核修正：原方案是「四处核数不等即判自检失败」，这只在两台没有屏蔽核的芯片上验证过。改为核数不等时降级成「只显示每核、不分簇」，不让整个模块失败。
- 复核修正：参考实现 `topo_discover.h` 的 `td_assignPerfLevels` 只取「数量法 → 频率法 → L2 法」中第一个有结果的，**没有交叉核对，也没有 degraded 标志**。用合成输入测试时（频率和 L2 都与数量法相反），它静默给出数量法的结果（`sk_conflict.txt`）。数量法也没检查整体是否一一对应。产品实现必须补上这两点，不能照搬参考实现。
- 不用 `HOST_CPU_LOAD_INFO`：它受全系统节流，20 Hz 下 M5 有 28/39、M2 有 32/39 次拿到陈旧值。本进程单独 1 Hz 调用时是 0/7，但这份额度与其他第三方 app 共享。
- IOReport 簇通道的「非 IDLE 驻留」不是占用率：M2 空闲时 E 簇通道有 71.6% 时间活跃，而 E 核平均只忙 20.7%。簇通道只用来算频率。

### 2.2 频率

| 指标 | 推荐来源 | M5 | M2 | 开销 | 私有 | 发现方法 |
|---|---|---|---|---|---|---|
| 每簇实际频率 | IOReport「CPU Stats / CPU Complex Performance States」中的实际频率簇通道：各 V 状态驻留 × DVFS 表，按活跃驻留加权平均 | 可用：通道 MCPM0 / MCPM1 / PCPM。与内核按档 cycles/时间相比，多核 0.00%，单核 −0.36%，BACKGROUND +0.19% | 可用：通道 ECPM / PCPM / PCPM1。安静时多核 0.00%，BACKGROUND +0.24%。P 簇单核 3503 MHz，多核上限 3264 MHz，E 簇全核 2424 MHz | 真实节奏每次 M5 9.4–9.7 ms（1 Hz 约 0.95% 单核，5 s 约 0.19%）；M2 2.9–3.4 ms（1 Hz 约 0.3%，5 s 约 0.07%） | 是 | 按结构规则认通道，不按名字（§7.2） |
| DVFS 频率表 | pmgr 节点的 `perf-domains` 给出「域名 → 表键号」，再读 `voltage-states<k>-sram` | 可用：单位 kHz。Super 20 档 1308–4608 MHz，M 簇 15 档 1344–4380 MHz；另有 `acc-clusters` 可作旁证 | 可用：单位 Hz。E 簇 6 档 912–2424 MHz，P 簇 17 档 702–3504 MHz；没有 `acc-clusters` | 启动一次，1.8 / 3.3 ms | 否（未文档键） | 域名与请求簇通道名逐字相等；单位按量级判断 |
| 每簇 / 每核请求频率 | 同一订阅里的请求通道（簇：M5 为 PCPU/MCPU0/MCPU1，M2 为 ECPU/PCPU/PCPU1；逐核通道按出现顺序对应 logical cpu） | 受限：多核时 Super 高估 8.8% | 受限：多核时 P 簇高估 7.35% | 与实际频率同一订阅，不另计 | 是 | 只进诊断页；实际通道缺失时作回退，标「估算」 |

- 复核修正（原结论被推翻）：开销。拓扑频率视角在紧循环里测到 M5 4.8–5.2 ms、M2 1.24–2.04 ms。但按 1 Hz 真实节奏醒来时，采样线程几乎总是落在较慢的一档（M5 落在 M 核，M2 落在 E 核），每次开销约翻一倍：M5 utility QoS 三次中位数为 9.36 / 9.36 / 9.55 ms，M2 为 2.86–3.23 ms。提高 QoS 没有用，user-interactive 在 1 Hz 下也落在慢档。A/B 实验表明开销没有转嫁给内核或其他进程，线程 CPU 时间就是全部开销。
- 复核修正（部分）：同一驱动的多个组合并进一个订阅时，开销约等于其中最贵的一组，不是固定的一份。紧循环实测：M5 上 CPM 4.7–5.1 ms、Energy Model 5.5–6.4 ms，合并后 6.4–6.6 ms；M2 上 CPM 1.9–2.0 ms、Energy Model 3.8–4.1 ms，合并后 4.0 ms。不同驱动合并则开销相加（CPM + 中断统计：M5 9.9 ms，M2 7.4 ms）。
- 复核修正（原结论被推翻）：建一次订阅的 62 ms（M5）/ 79 ms（M2）几乎全花在 `IOReportCopyChannelsInGroup` 上：进程内首次 64 / 75 ms，之后每次 28–31 / 39–40 ms，与组名无关。`IOReportCreateSubscription` 本身只要 0.12–0.33 ms。所以通道字典要全 app 共享一次枚举。
- 复核修正（部分）：CPU 域的无后缀表（如 M2 的 `voltage-states1`、M5 的 `voltage-states5`）第一列是常数，不是频率表，不能作回退。合法性检查要改成「严格递增」，并拒绝常数列。
- 复核修正（部分）：单线程主动自检只能证明 perflevel0 那张表是对的。它分不出实际通道和请求通道：单线程窗口里请求通道的误差只有 −1.12%～+1.70%，也能通过 ±5% 的阈值。它也覆盖不到较慢一档的表。因此要加被动校验（§7.5）。
- 同一档内两个簇的频率可以相差很大：M5 6×UI 负载时 MCPM0 2979 MHz、MCPM1 1372 MHz；M2 1×UI 时 PCPM 3503 MHz、PCPM1 1181 MHz。频率必须按簇给出，不能按档合并。
- 驻留是积分量：驻留增量 / 墙钟 = 0.97–1.02 × 24 MHz（即 timebase 频率）。拉长采样间隔不会丢失窗口平均值。

### 2.3 温度与热状态

| 指标 | 推荐来源 | M5 | M2 | 开销 | 私有 | 发现方法 |
|---|---|---|---|---|---|---|
| CPU 每簇温度（簇内最高） | SMC `T*` 键（只读，AppleSMC selector 2），按芯片档案和运行时回归归簇 | 可用：Super = `Tp0*` 18 键（`Tm0y`、`Tm2T` 是 `Tp0a` 的别名）；M 簇0 = `Tm0*` 17 键 + `Tm1E`、`Tm1I`；M 簇1 = `Tm1M/Q/U/Y/c/g/k/o/s/x` + `Tm21/25/29/2D/2H/2L/2P/2j/2n` 共 19 键；`Tm1p` 不是 CPU 温度，排除 | 受限：两个 P 簇可以分开。`Tp0*` 的 8 组三元组 → cluster-id 1（cpu4–7）；`Tp1A–Tp1O`、`Tp1g–Tp1u` 的 8 组 → cluster-id 2（cpu8–11）。E 簇只有弱候选 `Te04/05/06`，待复测 | M5 最小集（约 56 键）2.3–2.6 ms CPU，但 SMC 读取是阻塞的，墙钟约 12–15 ms；M2（16 键）0.7–0.8 ms | 是 | 不按键名：回归 + GPU 自变量 + 聚合键检测（§7.3）；芯片档案由实测生成 |
| CPU 最高温 | 已归簇键与「CPU 共享」键的最大值 | 可用：df18 负载时 Super 最高 77.6 °C | 可用（只含 P 簇）：ui8 时 60.5 °C | 与每簇温度同一次读取 | 是 | 归簇收敛前用相对判据：GPU 贡献比 g < 约 0.65 |
| M2 温度键的三元组变体 | x0 原始 / x1 = x0 + 常数偏移（4.633 或 6.700 °C）/ x2 尖峰读数 | 无此结构 | 用 x1（纯 CPU 负载下，SMC 自己的 `TCMb` 恰好等于 x1 的最大值）；x2 只作「峰值」 | — | 是 | 运行时检测「某键 = 某组键的逐秒最大值」 |
| 热状态 | `ProcessInfo.thermalState` + notify `com.apple.system.thermalpressurelevel` | 可用：所有 ≤60 s 的负载中都停在 nominal | 可用：同左 | 读取约 0.03 µs；用通知回调时为 0 | 否 | 公开 API，不需要发现 |
| HID 温度传感器 | 私有 IOHIDEventSystemClient | 不能用于 CPU：70 个服务、24 个名字，只有 PMU 和 NAND | 不能用于 CPU：57 个服务，没有 pACC/eACC，对 CPU 负载响应 <1.2 °C | — | 是 | 不用 |
| SoC 热点 | `TCMb`、`TVD*`、`TPDX` 等 | 随 GPU 升温（GPU 31 W 时 TCMb 从 50 升到 66 °C） | 同样随 GPU 升温；`TPD*` 对 CPU 负载几乎不响应 | — | 是 | 划给功耗与散热 |

- 复核修正（M5 的归属，部分）：`Tm1E`、`Tm1I` 在三种独立的负载设计中都表现为 M 簇0 的键。`Tm1p` 对任何负载都不响应，空闲时却比 CPU 键高约 5 °C；按名字把它算进 M 簇1，会让空闲时的「簇最高温」虚高 4–5 °C。这说明芯片档案和算法评估用的「真值」都必须来自实测，不能来自键名。
- 复核修正（M2 的 E 簇，部分）：原结论「E 簇找不到传感器」依据的是 bg4 负载，但 background QoS 把 E 簇压在低频（PPSR 只 +0.1 W），激励不足。改用功率作自变量回归后，`Te04/05` 对 E 簇 0.74 °C/W，对 P 簇 0.15 °C/W，对 GPU 0.085 °C/W，是 E 簇选择性最高的键。只是 E 簇满载功率只有约 1.4 W，绝对升幅约 2 °C。需要在 M2 上用 ui8↔ui12 翻转复测，再决定要不要给 E 簇温度行。
- 复核修正（原结论被推翻）：归簇收敛前的降级口径原写「对 GPU 功率无响应的键」，按这个字面判据，M5 上一个 CPU 键都留不下：GPU 约 18.7 W、CPU 空闲 20 s 时，所有 CPU 簇键都升了 7–8.7 °C；M2 在 GPU 38 W 时升 3.5–4.2 °C。改用相对判据（GPU 贡献明显小于 CPU 贡献），并在 UI 上说明簇温度是「簇所在位置的温度」，GPU 重载时也会升高。
- 复核（部分）：温度归簇算法有 4 个会造成显示错误的缺口。① x2 尖峰键与 x1 不是恒定偏移，别名合并吸收不了，会被当成独立组判入簇，使簇最高温平均偏高 3.1 °C（95% 分位 7.5 °C，最大 12.9 °C）。② 回归里没有 GPU 自变量，`TCMb`、`TVD0` 等 SoC 热点会被并进 Super 簇，显示值在空闲时偏高 9 °C、GPU 负载时偏高 17 °C。③ 评估用的真值来自键名正则，M5 上有 3 个键是错的，原模拟的识别率要重算。④ 按每单位占用归一化会系统性低估 E 簇、M 簇这类小功率簇，应改按每瓦敏感度。修正写进 §7.3。
- 复核确认：M2 三元组的偏移恒定（差值标准差为 0）；SMC 温度和功耗键每秒更新一次（20 Hz 采样时，变化间隔中位数 1000–1009 ms）。

### 2.4 CPU 功耗（边界参考，建议划给「功耗与散热」）

| 指标 | 推荐来源 | M5 | M2 | 开销 | 私有 | 发现方法 |
|---|---|---|---|---|---|---|
| CPU 实时功耗 | M5：SMC `RP00`+`RP01`（Super）、`RP02`（M 簇0）、`RP04`（M 簇1）。M2：没有专用键，只能估算 | 可用：按簇给出，不含 GPU（GPU 31 W 时 RP00–04 不变） | 受限（估算）：P 簇 ≈ `PSVR` − AGX GPU 实时功率 − 底噪；E 簇 ≈ `PPSR` − 0.034 × GPU − 底噪；都要用 PMGR 批次校正 | M5 读 4 个键 0.1–0.16 ms；M2 读 PSVR 0.04 ms，加上只订阅 AGX「GPU Energy」1.7–1.9 ms | 是 | 功耗轨回归：以每簇占用和 GPU 实时功率为自变量；GPU 贡献 <10% 且单簇主导的就是该簇的专用轨 |
| CPU 30 分钟均值 | IOReport Energy Model（PMGR） | 可用：每 1800 s 一批，相位 = 开机 + 193 s | 可用：同样每 1800 s 一批，相位 = 开机 + 92 s | 整组 M5 6.8–13.6 ms、M2 5.7–8.4 ms；每 60 s 检查一次即可 | 是 | 按计数器变化检测批次；簇 = Σ每核 + Σ每核_SRAM + CPM + CPM_SRAM |

- 复核修正（部分）：M2 PSVR 的数字应为 ui4 +9.5 W、ui8 与 ui12 都是约 +18 W（原写 +8.5 / +14.9 / +18.1 W）。ui8 ≈ ui12 说明 PSVR 不含 E 簇。「估算比 PMGR 偏高至少 8–12%」只来自一个缺了开机后 112 s 的不完整窗口，而且底噪定义能让比值移动 ±3–4%。第二个完整窗口的 SMC 积分留在远端，因 ssh 中断没有取回。
- 复核修正（原结论被推翻）：「M2 的 E 簇份额不能实时分离」不成立。`PPSR` 是以 E 簇为主的供电轨：E 簇满载 +1.43 W，而对 P 簇只有 0.07–0.08 W/满载。窗口 1 中 `PPSR − 底噪` 的积分是 PMGR EACC 的 0.96–0.98（下限）。
- 复核修正（原结论被推翻）：Energy Model 里「簇级通道 = 同前缀每核通道之和」不成立，后者只占前者的 0.63–0.69。精确成立的是「簇 = Σ每核 + Σ每核_SRAM + CPM + CPM_SRAM」（误差 ≤0.1 J）。M5 Super 簇的每核通道叫 `PACC_n`，按前缀认簇会失败。PMGR 的 PACC0/PACC1 与 cluster-id 1/2 的对应关系仍未验证。
- 复核修正（数字）：M2 上 PMGR 的 GPU0 比 AGX 实时积分至少低 10%（按覆盖时长外推约 16%）；M5 上两者只差 0.01%。

### 2.5 进程与 Top N

| 指标 | 推荐来源 | M5 | M2 | 开销 | 私有 | 发现方法 |
|---|---|---|---|---|---|---|

- 复核确认：多成员 coalition 和 kernel_task 所在的 cid 1 也准（M5 3.93% 对 3.85%，M2 6.07% 对 6.00%）。窗口内已退出的短命子进程的 CPU 也计入了，按进程的视图会漏掉其中 84–98%。
- 复核修正（原结论被推翻）：「最后一个成员退出后 coalition 仍可读」不成立。两台各被动观察 60 s，消失的 6 个 coalition 在消失前都没出现过 tasks==0，而是在最后一个成员退出的同一轮轮询里直接从列表中消失；列表里 tasks==0 的那些是常驻的 launchd job。因此每应用历史必须按 tick 累加增量；每分钟才读一次，会把寿命不到 1 分钟的应用整段漏掉。
- 复核修正（部分）：开销。M2 的 0.83% / 0.42%（1 s / 2 s）是在其他 agent 重负载（load 5–13）下测的，负载较轻时约为 0.68% / 0.35%，与 M5 相当。分层扫描（每 2 个 tick 做一次全量）实测 0.47–0.50%，不是约 0.4%；每 5 个 tick 一次全量才稳定在 0.31–0.35%。
- 复核修正（部分）：原自检 S3 要求「恰好写出 400 字节」，这是等值判断。将来结构体尾部追加字段时它会误判失败（26.x 是 360 字节，27 已扩到 400）。改为「≥400 且 slot 23 == 7」，语义交给 S4/S5 的实测判断。
- 复核修正（原结论被推翻）：「UI QoS 自旋 50 ms 做频率签名自检」在 M2 上不可靠。新进程里的短自旋线程先落在 E 核，50 ms 时 p 占比 >90% 的次数只有 0/20 和 6/20。要做的话，自旋至少 200 ms，失败就稍后重试，不要永久隐藏。
- 复核（部分）：perflevel0 占比的数值是准的，但它由调度器按线程组放核决定，不代表应用本身的性质。同样的工作量，密集执行时 p 占比 73–75%，每个子进程退出前多睡 20 ms 就降到 0–2.4%。
- 复核（部分）：能耗要等上下文切换才结算，短命进程自己读到的能耗偏低；1–2 s 窗口的汇总不受影响。
- 复核修正（数字）：进程视角写的 M2「834/835 可读、空 coalition 139/140 仍可读」在证据文件里找不到。文件（26A434）里是 651/652 可读、空 coalition 72/73 可读，结论不变。
- 对照口径：`top` 的 %CPU 列对忙进程偏低（复核：1 s 窗口约 9–10%，5 s 窗口约 2%。原视角在 M2 重载时测到 35–45%，复核在轻负载下没有复现）。验收对照改用 setuid `/bin/ps` 的 TIME 差分（10 ms 分辨率，覆盖除 pid 0 外的全部进程），kernel_task 单独用 `top -l 2 -s N -pid 0`。
- 在「按进程」视图里，外部（root 和其他 uid）进程两台都有 77% 独占一个 coalition、可以精确显示，约 1% 可以用残差算出，22–23% 只能按组显示（如 coreaudiod 组、WindowServer + MTLCompilerService、kernel_task + launchd）。

## 3. 与调研报告不同的发现

### 3.1 M2 上的意外

1. **Mac Studio 调研中途自动更新并重启**：05:11 关机（有 shutdown_stall 报告，是正常关机流程，不是 panic），05:12:41 开机后变成 macOS 27.0.1（26A434）。D25 登记的「两台都是 26A428」已不成立，M5 仍是 26A428。重启清空了远端 /tmp。M2 的拓扑、DVFS 表、IOReport 通道结构、coalition 布局在两个 build 上相同。按 K19，这也是一次「系统 build 变化即复检」的实例。
2. **M2 也有实际频率通道**（ECPM / PCPM / PCPM1），命名语法与 M5 相同，但同名不同义：`PCPM` 在 M5 上是 Super 簇，在 M2 上是第一个 P 簇。
3. **DVFS 表的频率单位随芯片变**：M2 是 Hz，M5 是 kHz（u32 装不下 4.6 GHz 的 Hz 值，这可能是 M5 改用 kHz 的原因）。
4. **核档同名不同位**：「Performance」在 M2 上是 perflevel0（最快），在 M5 上是 perflevel1。cluster-type 字母在 M2 是 E/P，在 M5 是 M/P，同一个「P」在两台上分别是 Performance 和 Super。M2 最慢的 E 簇是 cpu0–3；两台上 perflevel0 都碰巧排在最高号，算法不依赖这一点。
5. **M2 没有 CPU 专用的实时功耗键**：没有 RP*，也没有 PZD1（DRAM 实时）。`PC00–PC42` 名字像 CPU，其中 PC10/12/20/22 实测是 GPU 轨。唯一随 P 簇变化的 `PSVR`/`PSVC` 同时承载 GPU（GPU 38 W 时 PSVR 39.6 W）。
6. **M2 的温度键是三元组**；社区工具当作「M2 E 核温度」的 `Tp1*` 实际随第二个 P 簇变化；整个 SMC 里只有 `Te04/05/06` 是 E 簇的弱信号候选。
7. **HID 温度缩水、Energy Model 按 30 分钟批次发布**，在 M2 上同样存在，是 macOS 27 的全局行为，不是 M5 特有。批次相位随机器不同（M2 为开机 + 92 s，M5 为 + 193 s，对 1800 取模），只能按计数器变化检测。
8. **M2 的 PMGR 采样便宜得多**：真实节奏每次约 3 ms，M5 约 9.5 ms。
9. **M2 的 DT `l2-cache-size` 与 sysctl 不一致**：P 簇在 DT 里写 8 MB，`hw.perflevel0.l2cachesize` 是 16 MB，所以 L2 只能用来比大小。
10. M2 上 `PROCESSOR_CPU_STAT64` 的中断余量是设备中断数的 3 倍，原因未知。
11. M2 的 PMP 组名是「PMP」而不是「PMP0」，也没有 Energy 直方图（给功耗模块）。
12. **SysInfo app 的菜单栏和面板从没在 M2 上运行过**，M0 在 Mac Studio 上只跑过 CLI。按档分组、柱宽、温度和频率行的显示都要在 M2 上实际验收。

### 4.2 划给「功耗与散热」（下一个模块）

- ~~CPU 实时功耗~~：已按 C1 = B 移入 CPU 模块（2026-10-15）。留在这里的只有：按 PMGR 系数校准（K35），以及给没有专用轨的芯片（例如 M2）做估算，是否要做由功耗模块再议。原文：M5 按簇读 RP*；M2 为 PSVR/PPSR 估算加 PMGR 批次校正；是否按 PMGR 系数校准（K35）也在那时定。理由：M2 上要减去 GPU 实时功率、用 PMGR 批次校正，属于跨域计算；M2 估算的精度还没定论（完整窗口的数据没取回）。那个模块完成后，CPU 面板加一行 CPU 功耗并链接过去。
- SoC 热点（TCMb、TVD*、TPDX 等）、完整传感器目录、风扇读数。
- PMGR 30 分钟批次与分部件明细（K36）；整机、SoC、GPU、DRAM 功耗。

### 4.3 划给「应用活动」

- 每应用的 GPU、ANE、磁盘、内存、能耗与功率列：复用 AppSampler 和 `app_minute` 表，按列扩展。
- 按应用浏览较长时段的历史窗口。
- 理由：这是跨域视图（D13）；CPU 模块只做 CPU 这一列。

### 4.4 不做

| 不做 | 理由 |
|---|---|
| 系统级上下文切换 | 没有免 root 的系统级计数器；部分合计（约 60% 的进程）容易被误读成系统值 |
| 每核频率、请求频率进主界面 | 同簇的核共用一个时钟，「每核频率」没有独立的物理含义；请求频率多核时高估 7–9%；二者只在诊断页出现 |

| HID 温度 | 两台都没有 CPU 传感器 |
| 定时 spawn `top` / `ps` | 开销和精度都不合格（D05 的回退另议，见 C5） |
| 提权结束进程 | D04：root 只用于风扇 |
| 用 IOReport 簇通道的「非 IDLE 驻留」当占用 | 它不是占用率 |

## 5. CPU 模块产品方案（草案）

以下按 §6 各题的推荐选项写成，你改选后相应调整。

### 5.1 菜单栏（K40、K42）

- 默认采用上下布局（C7 已定）：上行是小号标签「CPU」，下行是等宽数字的数值「23%」。宽度按「100%」的字宽固定，约 32–36 pt，约为 M0 左右布局（64 pt）的一半，给后续多个模块留出菜单栏空间。可参考 Stats 的 mini widget：标签 7 pt，数值 12 pt，宽 31 pt 加边距。具体字号以 27 菜单栏的实际高度截图自查后定。左右布局「CPU 23%」作为可选样式保留。
- 可选样式：
  - 数值；
  - 双行：占用 + 第二值，第二值可选温度、负载均值或频率（频率是高开销项，要标注开销）；
  - 迷你折线：30 / 60 / 120 s，可叠加数值；
  - 柱状：总量 / 按档 / 每核。每核柱宽 = 核数 × 约 3 pt（M5 约 60 pt，M2 约 42 pt），启动时按拓扑算一次，运行中不变。
  - 不做饼图和仪表盘；带变量的文本模板放到 P1。设置页的预览直接用真实的 item view 渲染。
- 着色：平时单色。对总占用做 EMA（τ = 1.5 s），持续 10 s ≥85% 变 systemOrange，≥95% 变 systemRed，回落时留 5 个百分点滞回。阈值放在共享配置里，P2 的提醒直接复用。温度不参与着色。
- 「合并为单个 item」按 D15，等菜单栏有 3 个模块时再做。

### 5.2 面板（CPU tab）

从上到下：
1. **概览**：大号总占用 + 用户/系统细分条。右侧三个小值：最快档的实际频率（最近一次 5 s 平均）、CPU 最高温度、热状态徽标（正常 / 偏高 / 严重 / 危急）。
2. **历史图**：2 分、15 分读内存环形缓冲（1 s 一点，保留 15 分钟，按 K39 推荐）；1 时、24 时、7 天读历史库，画成均值线加峰值带，睡眠等空洞处断开。默认 2 分。
3. **核心**：按档分组，快档在前（按 perflevel 序号排，不按核编号）。组标题形如「超级核 ×6 · 45% · 62 °C」。每簇一行：占用、实际频率、簇温度。每核柱按档着色。
   - 簇几乎不活跃时，频率显示「空闲」，不显示 0 或最低档。
   - 档名取 `hw.perflevelN.name` 并本地化：Super → 超级核，Performance → 性能核，Efficiency → 能效核（暂定译名）；不认识的名字原样显示。颜色按名字取，不认识的名字按序号取备用色；MetricID 按序号（如 `cpu.usage.perflevel.0`）。这样两台上同名的「性能核」颜色一致，而快慢语义只看序号。
   - 档次判定为 degraded 时不做档汇总，只列簇。
   - 没有可辨识传感器的簇不显示温度（M2 的 E 簇待复测）；诊断页注明原因。
   - 温度旁加一句说明：「簇所在位置的温度，GPU 重载时也会升高」。
4. **详情**（默认折叠）：负载均值（注明约 5 s 更新一次）、开机时间、进程与线程数、中断（每秒的 IPI、定时器和其余三项，口径写明）。展开「中断来源」时才按设备列出 Top N（C8）。
5. **Top N**：见 §5.3。

面板内的采样只在 CPU tab 可见时进行：占用 1 s，频率 5 s（C4），温度 2 s，Top N 2 s，中断 1 s（`PROCESSOR_CPU_STAT64`，约 10 µs/次）。

### 5.3 Top N（K37、K38）

- 数据：coalition 全量扫描，CPU tab 可见时每 2 s 一次；按区间 CPU% 排序（单核 = 100%）；默认 5 行（可选 0/3/5/8/10）；鼠标悬停在列表上时冻结排序，防止误点。
- 行：一个 coalition 一行（C5）。行名依次取：`NSRunningApplication` 登记的成员（regular > accessory > prohibited，同级取最早启动的）→ 路径里有最外层 .app 的成员 → 最早启动的成员，并加「等 N 个」。终端、Xcode 这类宿主 coalition 的副标题显示占比最高的成员，如「终端 · claude 6.4%」。
- 展开：同 uid 成员用 libproc 精确拆分；外部成员只能归入「其余 N 个进程」这个残差。残差只在窗口内 slot 0/1（tasks_started / tasks_exited）没有变化时才算，否则短命子进程的 CPU 会被错算到 root 成员（如 login、sshd-session）头上；残差钳到 ≥0。展开行也显示 perflevel0 占比，只在两档芯片上显示，并注明「由系统调度决定」。
- 设置里可以切换到「按进程」视图（外部进程约 22% 只能按组显示）。
- 结束进程：GUI app 用 `NSRunningApplication.terminate()`，其他同 uid 进程用 SIGTERM；一律先弹确认，按住 ⌥ 默认强制（`forceTerminate()` / SIGKILL）。组行、root 与其他用户的进程、SysInfo 自身不显示按钮。
- 已退出的应用：coalition 会立即消失，只能保留它消失前最后一次采样的数据。
- 回退：coalition 自检失败时，只显示同 uid 进程，提示「另有 N 个系统或其他用户进程不可见」，并提供手动「刷新全部」按钮：间隔 2 s 运行两次 setuid 的 `/bin/ps -axo pid=,time=`，取 TIME 差分，约 0.2 s CPU，只在点击时发生。

### 5.4 设置页（CPU）与诊断页

- **采集**：模块采集间隔覆盖（已有）；面板内频率、温度、Top N 的刷新间隔可选 1/2/5 s。这是 D25「全局 + 逐模块」之外新增的逐项间隔，依据是 D19。
- **菜单栏**：样式、「CPU」标签开关、双行的第二值、折线时长、柱状模式、着色方式与阈值、实时预览。
- **面板**：图表默认跨度、是否拆分用户/系统、Top N 行数、分组方式（按应用 / 按进程）。
- **高开销选项**：每项标注「约 +x% 单核」，数值取诊断页里本机实测的滑动平均；还没有实测值时，显示参考值并注明「参考 M5 Pro / M2 Max」。包括：
  - 菜单栏显示频率：M5 在 1 s 周期约 +0.95%，5 s 约 +0.19%；M2 在 1 s 约 +0.3%；
  - 面板 1 s 刷新；
  - 后台高精度历史（频率和温度 5 s 一次）。
- **历史**：记录 CPU 历史、记录每应用 CPU、保留期、清除每应用数据；链接到「历史与导出」页。按 D27，隐私页的「数据存放」加上历史库路径。
- **诊断页**：
  - 每个数据源的状态和当前走的路径：实际频率还是请求频率；温度归簇来自芯片档案、学习中还是已校准；Top N 用 coalition 还是同 uid 回退；

  - 「传感器校准」按钮（C6）；
  - 请求频率和逐核频率只在这里显示。

### 5.5 历史存储（C2、C3、K33、K34、K39）

- 引擎：系统 libsqlite3（两台都是 3.54.0；本机 PATH 里的 `sqlite3` 命令行是 3.53.2，不能用它判断特性），WAL + `synchronous=NORMAL` + `auto_vacuum=INCREMENTAL`，用 `user_version` 做迁移。
- 位置：`~/Library/Application Support/<bundle id>/History.sqlite`，Debug 与 Release 隔离（D16）。
- 表结构（草案）：

  ```
  metric(id INTEGER PK, name TEXT UNIQUE, unit TEXT)
  epoch(start_t INTEGER PK, model, chip, os_build, topology_json)
  sample_minute(t /*UTC Unix 分钟*/, metric, avg REAL, max REAL, n /*覆盖秒数*/, q /*最差质量*/,
                PRIMARY KEY(t, metric)) WITHOUT ROWID
  sample_hour(结构同上，t 为 Unix 小时，按 n 加权汇总)
  app(id PK, key TEXT UNIQUE /*bundle id 或可执行路径*/, name)
  app_minute(t, app, cpu_ns INTEGER, energy_nj INTEGER, PRIMARY KEY(t, app)) WITHOUT ROWID
  ```

  - 表里没有与芯片相关的列。拓扑（档名、核数、簇）、机型、系统 build 记在 epoch 表里，变化时新开一段（包括用迁移助理把库带到另一台 Mac 的情况）。
  - 以后各模块用 ADD COLUMN 给 `app_minute` 加 GPU、ANE、磁盘等列。
- **主键必须时间在前**。实测 80 行/分、每分钟提交时，(metric, t) 主键的物理写入是 762 MB/天，(t, metric) 只有 60 MB/天；前者的小时汇总还会随表变大而变慢（30 天时 32 ms，后者 1.3 ms）。代价是读单个指标 24 小时的分钟数据约 2 ms，可以接受。
- CPU 每分钟约 12–13 行，随拓扑变化：total/user/system、每档占用、每簇频率、每簇温度（只含有传感器的簇）、负载均值、热状态最高级。每行带 avg、max、n、q。每核数据不入库。
- 写入：内存里按分钟聚合，每 5 分钟一个事务；睡眠、退出、导出前立即提交，崩溃最多丢 5 分钟。整点后 1 分钟做小时汇总；保留期清理每天一次（DELETE + incremental_vacuum）。
- 空洞：睡眠期间不写行；唤醒后第一个差分丢弃（M0 已有 resetBaseline）；计数器回退按复位处理、丢弃这一段；墙钟回拨造成主键冲突时，用 UPSERT 按 n 加权合并。
- **面板关闭时的采样**（K06 遗留）：历史记录器登记 background 层需求（锁屏、显示器睡眠时继续采）。
  - CPU tick：菜单栏 item 开着时复用 1 s 样本，否则每 60 s 读首尾差分。
  - 频率：IOReport 驻留每 60 s 差分，得到精确的分钟平均频率，但没有峰值。
  - 每应用 CPU：coalition 每 10 s 扫一次，按 tick 累加（C3）。
  - 温度每 10 s 一次；负载均值、热状态每 60 s 一次。
  - 峰值精度：菜单栏开着时占用为 1 s；否则占用和频率只有均值（max 记为空，不假装有峰值），温度为 10 s。
  - background 层不受降频（slowed）影响，避免分钟桶错位。
- **导出**：在「历史与导出」页手动触发，可选时间范围、粒度（分钟 / 小时）、指标组和格式。CSV 导出为一个文件夹：`system.csv` 是宽表（ISO 8601 时间，每个指标 avg、max 两列，空洞留空），`apps.csv` 是长表，`metadata.json` 写机型、芯片、档名与核数、单位和 app 版本；JSON Lines 为长表，首行是元数据。序列号、UUID、MAC、IP 本来就不入库；机型标识和芯片名不是唯一标识，默认包含。实测 30 天 P0 规模（345 万行）全表扫描 142 ms。
- 实测开销：每 5 分钟一个事务 77 µs（M5）/ 114 µs（M2，开机后高负载，计时偏高）；小时汇总 0.1–0.18 ms；删一天 3–4.6 ms。CPU 模块单独约 0.6 MB/天，每应用前 10 约 0.42 MB/天，两台的字节数完全相同。

## 6. 需要你拍板的问题

### C1 温度、热状态和 CPU 功耗放在哪个模块？SMC 只读层在哪里建？（D15 待确认）· 已定：B（2026-10-15 用户改定）
- **已定**：选 B。CPU 实时功耗并入 CPU 模块，按簇显示；没有专用功耗轨的芯片显示为「不可用」（显式的数据质量状态），不做估算。温度、热状态徽标、SMC 只读层、芯片档案机制按 A 的内容一并在 CPU 模块里建立。SoC 热点、完整传感器目录、风扇和 30 分钟批次仍归「功耗与散热」。
- **A**：CPU 模块做 CPU 温度（按簇最高温、CPU 最高温）和热状态徽标。SMC 只读层（枚举、按 build 缓存 key-info、字节序与 result 字节检查）、温度键发现、芯片档案机制都在 CPU 模块里建立。CPU 实时功耗、SoC 热点、完整传感器目录、风扇、30 分钟批次归「功耗与散热」；那个模块完成后，CPU 面板补一行功耗。
- **B**：在 A 的基础上，CPU 实时功耗也放进 CPU 模块：M5 按簇读 RP*；M2 为 P 簇、E 簇的估算值，用 PMGR 批次校正，标注「估算」。
- **C**：CPU 模块不碰 SMC，只显示公开的热状态；温度和 SMC 层整体放到「功耗与散热」。
- **推荐 A**。温度方面：两台都能把温度键归到 P 簇（M5 三个簇，M2 两个 P 簇），和每簇占用、频率放在一起最有用；Stats 也把 CPU 温度放在 CPU 弹窗里。SMC 层反正要建，在第一个模块就把它和芯片档案在两台机器上跑通，风险最低。功耗方面：M2 没有 CPU 专用功耗键，要减去 GPU 实时功率并用 PMGR 批次校正，是跨域计算；估算精度还没定论（完整校准窗口的数据因 ssh 中断没取回）；K35 本来就排在功耗模块。温度视角原推荐 B，产品视角推荐 A，这里取 A。

- **2026-10-15 补充**：M4 Pro 和 M5 一样有按簇、不含 GPU 的专用功耗轨（§9.2）。推荐 A 的主要理由「M2 只能估算」已不适用于现在的两台目标机，建议改选 **B**。没有专用轨的芯片显示为不可用。

### C2 历史存储（D08）是否在 CPU 模块里实现？（D15 待确认，K33、K39） · 已定：A（2026-10-15 用户按推荐确认）
- **A**：并入。CPU 模块建通用历史库（系统 libsqlite3，§5.5），写入 CPU 指标；面板提供 1 时 / 24 时 / 7 天跨度；「历史与导出」页和面板关闭时的后台采样一并完成。
- **B**：CPU 模块只保留内存里 15 分钟的历史；P0 各模块完成后，单独做一个历史里程碑，所有模块一次接入。
- **C**：CPU 模块完成后、功耗与散热开工前，单独插一个历史库里程碑。
- **推荐 A**。D14 的完整版包含历史图表，K39 里 1 小时以上的跨度离不开历史库。库结构与具体模块无关（按 MetricID 存的长表），后续模块只需登记指标。后台层采样（锁屏时也继续）要在第一个用到它的模块里定型，晚做就得回头改 CPU 采集器。实测开销很小：每 5 分钟一个事务，约 0.08–0.11 ms CPU。

### C3 历史保留多久？记不记录每个应用的用量？面板关闭时多久扫一次 coalition？（K33、K34、K06 遗留） · 已定：A（2026-10-15 用户按推荐确认）
- **A**：分钟级保留 30 天，其中包括每分钟 CPU 用量前 10 的应用；小时级永久保留，只存整机指标。面板关闭时 coalition 每 10 s 扫一次，按 tick 累加（常驻约 +0.07%）。
- **B**：同 A，但 coalition 每 60 s 扫一次（约 +0.012%）；寿命不到 1 分钟的应用会整段漏记，图表和导出里注明口径。
- **C**：分钟级 7 天（含前 10 应用），小时级 1 年，天级永久。
- **D**：分钟级 30 天、小时级永久，不记每应用；每应用历史留给「应用活动」模块。
- **推荐 A**。体积按实测每行约 34 字节估算：只有 CPU 模块时，A 稳定在约 31 MB，每年另加约 3.6 MB；P0 全部完成后（约每分钟 80 行）约 130 MB，每年另加 24 MB；C 封顶约 56 MB；D 约 120 MB。30 天足够回答「上周那次卡顿是谁造成的」。每应用数据只存在分钟级，随分钟级一起过期，可以一键清除。coalition 在最后一个成员退出时会立即消失，每 60 s 扫一次会漏掉短命应用；10 s 一次的代价仍能让常驻合计保持在约 0.3%。进程视角建议把每应用历史留给应用活动模块（D），产品视角建议 A；取 A，是因为 AppSampler 和 `app_minute` 表本来就在 CPU 模块里建，早记录早有数据，应用活动模块以后加列即可。

### C4 实际频率默认怎么采？（K06、D19） · 已定：A（2026-10-15 用户按推荐确认）
- **A**：菜单栏默认不显示频率。面板 CPU tab 可见时每 5 s 采一次（驻留是积分量，显示的就是这 5 s 的平均，不丢信息）；后台历史每 60 s 采一次。设置里可以把频率加进菜单栏，或把面板改成 1/2 s，并标注本机实测开销。
- **B**：同 A，但面板内默认 2 s。
- **C**：常驻每 5 s 采一次，菜单栏默认就能显示频率（常驻增加 M5 约 0.19%，M2 约 0.07%）。
- **D**：常驻 1 Hz（M5 单这一项约 0.95%，约为出厂预算的 2 倍）。
- **推荐 A**。复核后的真实开销是 M5 每次约 9.5 ms、M2 约 3 ms，而且提高 QoS 也降不下来。按 §5.6 的估算，A 的面板合计在 M5 上约为 1.6% 加新增 UI；B 约为 1.9% 加新增 UI，大概率超过 2%；C 的常驻合计在 M5 上约 0.47%，贴线。频率是次要信息，D19 已经允许你自己把它放进菜单栏或调高频率，开销在设置里标明。
- **M4 补测（2026-10-15）**：M4 每次约 8.5 ms，和 M5 同一量级，而不是 M2 的 3 ms。所以「对照机便宜很多」的情况不复存在，两台都按约 9 ms 估算。
- **Stats 的做法**（`~/Documents/stats` 06c4dc1f，`Modules/CPU/readers.swift` 的 `FrequencyReader`，2026-10-15 读源码）：
  - 何时采：频率读取器标为 `popup`/`preview`。启动时读一次，之后只在弹窗或设置预览可见时运行，关闭即暂停。菜单栏 widget 不显示频率，也不进历史图表。
  - 节奏：跟随模块的更新间隔（默认 1 s）。每次 read 先取 1 个初始样本，再每 125 ms 取 1 个，共 4 次，做 4 次 delta 后取平均，即每秒 5 次 `IOReportCreateSamples`。
  - 数据源：订阅「CPU Complex Performance States」和「CPU Core Performance States」，按通道名子串（`ECPU`、`PCPU`、`MCPU`）取的是**请求频率通道**加逐核通道，同档各簇取平均。M4 多核时请求频率比内核实测高 17.1%（M5 高 8.8%）。
  - 频率表：按芯片代际写死 pmgr 的表键号（`voltage-states1/5/22-sram`），M4 起换一种解析格式（`isCpuStartFromM4`）。这正是 D20 禁止的写法。
  - 实测开销：用 C 复现它的节奏（`skeptic-topo-freq/sk_stats_freq.c`，不含 Swift 字符串转换，是下限），**弹窗打开时 M5 约 4.7%、M4 约 4.4% 单核**。同一探针测本方案的 5 s 节奏，两台都约 0.17–0.18%。
  - 可借鉴的是「频率只在面板可见时采、菜单栏默认不显示」，这与 A 一致。不借鉴的是它的节奏和通道：每秒 5 次采样的开销超过我们整个面板 2% 预算的两倍，请求通道在多核时偏高 9–17%。

### C5 Top N 怎么分行？能不能结束进程？coalition 失效时怎么回退？（K37、K38） · 已定：A（2026-10-15 用户按推荐确认）
- **A**：默认按应用，一个 coalition 一行，可展开看成员。终端、Xcode 这类宿主 coalition 保持一行，副标题显示占比最高的成员（如「终端 · claude 6.4%」）。设置里可以切换成「按进程」。同 uid 进程可以结束（先确认，按住 ⌥ 默认强制）；root 与其他用户的进程、组行、SysInfo 自身不显示按钮。coalition 自检失败时只显示同 uid 进程，另给手动「刷新全部」按钮（运行两次 setuid 的 `ps`，取 TIME 差分）。
- **B**：同 A，但把宿主 coalition 里有控制终端的同 uid 成员拆成独立的行，标「经 终端」（这是 K37 的原推荐）。

## 7. 实现要点

### 7.1 拓扑发现
1. 读 `IODeviceTree:/cpus` 的子节点，得到 logical-cpu-id → (die-id, cluster-id)。多 die 芯片上 cluster-id 是否全局唯一没有实测，所以簇键带上 die-id。
2. 校验 DT 核数 == `hw.logicalcpu_max` == `host_processor_info` 核数 == IOReport 逐核通道数。不等时降级为「只显示每核」。
3. 核类别键取 DT `compatible` 首串加 `cluster-type`，只当不透明字符串比较，不解释字母含义。类别数必须等于 `hw.nperflevels`。
4. 分别求三种「类别 → perflevel」映射，每种只在构成完整一一对应时才算有效：
   - 数量：类别总核数 = `logicalcpu_max`，簇大小 = `cpusperl2`，且匹配唯一；
   - DVFS 表顶频率降序对应 perflevel 0..n-1；
   - DT `l2-cache-size` 降序对应 perflevel 0..n-1（只比大小，M2 的 DT 值与 sysctl 不一致）。
5. 三种都求出来后两两核对，任何冲突都标 degraded，只输出每簇数据；三种都求不出（核数、L2 都相等且没有频率表）时标「无法确定」，不猜。合成输入测试覆盖了 M1 4+4、M1 Ultra 两 die、假想的三档芯片（`assign_sim.c`）。
6. 显示名用 `hw.perflevelN.name`。运行时用公开的 rusage v6（`ri_*_ptime`、`ri_pcycles`）被动核对映射。

### 7.2 频率发现
1. 逐核通道：子组「CPU Core Performance States」里按出现顺序第 k 条对应 logical cpu k。不要从名字解析核号（M2 是 3 位数字，M5 是 1–2 位）。
2. 请求簇通道：子组「CPU Complex Performance States」中，是本簇全部逐核通道名前缀的最长一条（M2 的 PCPU100–130 取 PCPU1 而不是 PCPU）。
3. 实际簇通道：状态名列表与请求通道完全相同、名字等长且只差一个字符、并且不是任何逐核通道名的前缀（M5 的 PCPM_IDLE 状态里有 NON_IDLE，因此被排除）。复核用「CPU → CPM 替换」的简单规则得到相同结果。
4. 状态名语法：DOWN、IDLE 算非活跃；`V<i>P<j>` 中 i 是表下标，两台上都满足 j = n−1−i。
5. DVFS 表：读 pmgr 的 `perf-domains`（每条 28 字节：byte0 为表键号，offset 12 起 16 字节为域名），域名 == 请求簇通道名 → 表键 k → `voltage-states<k>-sram`。只用 -sram 表，CPU 域的无后缀表不是频率表。单位按量级判断：最大值 ≥1e8 当 Hz，≥1e5 当 kHz。校验：表长 == V 状态数；严格递增、没有常数列、没有 0 档；表顶在 500–10000 MHz 之间。`perf-domains` 缺失时，只在 -sram 表里按状态数匹配；有歧义时把表顶最高的配给 perflevel0，并标「估算」。
6. 频率 = Σ(V_i 驻留 × f_i) / Σ 活跃驻留；簇活跃驻留约为 0 时显示「空闲」。
7. 找不到实际通道时退回请求通道，标「估算」并注明「请求频率」；两种都没有就隐藏这一行。
8. 芯片特有的多余通道一律忽略：M5 的 `*_IDLE` 和「CPU Complex Voltage State Time」，M2 的「CPU Complex DVD States」。

### 7.3 温度键发现（含复核修正）
1. 启动时全量枚举 SMC 键并按系统 build 缓存 key-info（M5 2455 键 14–23 ms，M2 1768 键约 20 ms，冷启动 81 ms）。字节序按属性位判断，支持 `flt`、`ioft`、`si32` 等类型，检查 result 字节。
2. 候选键：首字母 T、能解码、取值 10–125 °C、观察期内有变化。
3. 别名合并：两键差值的标准差 <0.05 °C 视为同一传感器（恒等或恒定偏移）。
4. **聚合键检测**（复核新增）：检测「某键 == 某组键的逐秒最大值」（如 `TCMb` == max(x1 组)、`TCMz` == max(x2 组)、`TPDX` == max(TPD*)）。聚合键本身排除；SMC 自己的 CPU 聚合所覆盖的那一组作为代表变体（M2 的 x1），x2 组只作峰值。
5. 自变量：按 cluster-id 汇总的每簇占用（1 s 滞后、τ≈1.5 s 一阶平滑），**加上 AGX GPU 实时功率**（复核新增）；有每簇功率时（M5 的 RP*、M2 由 VC0x 推出）优先按每瓦敏感度归一化，避免低估小功率簇。
6. 非负最小二乘。判入条件：R² ≥ 0.5、归一化贡献 ≥ 0.6、领先第二簇 ≥ 0.25、该簇有足够的独立激励（对其余簇回归后的残差标准差 ≥ 0.1）；并要求 GPU 贡献比 g = GPU 贡献 / 最大单簇贡献 < 约 0.65。离线验证中 M5 的 CPU 键 g = 0.16–0.40、TVD0 0.67、TCMb 0.80；M2 的 P 簇键 0.12–0.60、TCMb/TVD0 1.02。余量不宽，阈值要在更多数据上复核。
7. 对任何负载都不响应的键（如 M5 的 `Tm1p`）排除。
8. 收敛前的降级口径：对总 CPU 占用有显著正响应、且 g 小于阈值的键，取最大值作为 CPU 最高温。
9. 芯片档案与算法评估的真值只来自实测。校准用翻转激励：保持已满的簇不变，只翻转目标簇（M5 用 ui12↔ui18 翻转 M 簇1，M2 用 ui8↔ui12 翻转处于高频的 E 簇）；不用 background QoS。
10. SMC 读取是阻塞调用（M5 每键墙钟约 0.2 ms），放在独立 actor 上，不占用 SamplingActor 的 tick。

### 7.4 coalition 与 Top N
- dlsym `proc_listcoalitions`、`coalition_info_pid_list`、`coalition_info_resource_usage`；resource_usage 给 512 字节缓冲，要求写出 ≥400 字节且 slot 23 == 7。CPU 时间只用槽 24–30 之和，不用 slot 3。
- 成员列表缓冲按 tasks + 16 分配；返回大小等于缓冲大小时视为可能截断，加倍重试。
- 历史和 Top N 都按 tick 累加各 coalition 的增量；coalition 消失时，保留最后一次增量，不补推。
- 残差归因前先看窗口内 slot 0/1 是否变化；读取时刻的先后差会让残差出现 ±2.5 pp，钳到 0。
- 名称和图标的缓存键：私有的 `PROC_PIDUNIQIDENTIFIERINFO`（flavor 17）给出的 `p_uniqueid` 开机期间不复用，每 pid 0.16–0.37 µs，比 `KERN_PROC_PID`（5.5–12 µs）便宜 30–50 倍；公开路径用 (pid, 启动时间)，启动时间取自一次 `KERN_PROC_ALL`。
- 代表成员（行名）只对新出现的 cid 算一次，然后缓存。
- kernel_task 所在的 cid 1 是最贵的单次读取（冷态 M5 348 µs、M2 561 µs），而且总是活跃。

### 7.7 开销控制
- IOReport：全 app 只枚举一次通道字典（每多枚举一次，M5 多约 30 ms、M2 多约 40 ms）；同一驱动的组合并进一个订阅（开销约等于最贵的一组）；不同驱动（如中断统计）单独订阅、按需启停。
- 测开销要按真实节奏测首次调用的线程 CPU 时间，并记录线程落在哪一档；不要用紧循环。采样线程保持 utility QoS，提高 QoS 不省开销。
- SMC：读取放在独立 actor；只读最小键集（M5 去掉别名 `Tm0y`/`Tm2T` 和非 CPU 的 `Tm1p` 后约 56 键）；key-info 按 build 缓存。
- coalition：只在有消费者时扫；Top N 用全量，必要时改分层扫描（每 5 个 tick 一次全量）；名称、图标、代表成员都缓存。
- 公开计数器优先：占用用 `host_processor_info`，中断常驻只用 `PROCESSOR_CPU_STAT64`。
- 所有采样挂在同一个合并 tick 上，面板内的采样只在 CPU tab 可见时登记需求。

### 9.3 温度键：新陷阱、三元组与归簇

**新陷阱：断电占位值**（M5、M2 的实测里没有出现过）
- 全部 102 个 `Tp*` 键在所属区域断电时读出**恰好 40.0**。三份记录里有 49% 的样本是这个值，空闲时整簇都是 40.0。
- `Tg*` 键在 GPU 空闲时读出 −4.0 或 0.0，`Ta*`、`Tz*` 和少数 `T?DF` 恒为 0。
- 如果按普通数值处理，空闲时会显示「40 °C」，回归和归簇也会被这些平台值带偏（本节第一版回归就是这样，见 `m4_attrib.txt`）。
- 实现要求：
  - 把「精确等于 40.0 / −4.0 / 0.0」识别为**无读数**，显示为「—」，数据质量标为不可用，不用 0 或 NaN 代替（CLAUDE.md 硬性规则）；
  - 簇最高温只在本簇有有效读数时给出，没有有效读数时退到「CPU 最高温」，或显示「—」；
  - 占位值写进芯片档案，同时让运行时检测「长时间精确等于某个常数」的键。

**三元组**：和 M2 一样是 x0 / x1 / x2 结构，x1 = x0 + 常数，偏移有 5.5、6.3、9.2 °C 三种（例如 `Tp01 = Tp00 + 6.3`，`Tp0D = Tp0C + 5.5`，`Tp0m = Tp0l + 9.2`），x2 是第三个键。显示口径沿用 M2 的做法（显示 x1，x2 只作诊断页的峰值），这需要在 M4 上用 SMC 自己的聚合键再核对一次（§9.5）。

**归簇**：方法见 `m4_attrib2.py`。ui5 段里 5 个线程整体约每 2 s 在两个 P 簇间切换一次，形成天然的方波。对每个键做 4 s 高通后，与 util_P0 − util_P1 求相关；E 簇用 ui10↔ui14 翻转；GPU 用 30 s 的 Metal 负载。

| E 簇（弱） | `Te04`/`Te05`/`Te06`、`Te0R`/`Te0S`/`Te0T`、`Tex0`–`Tex3` | 每瓦敏感度：E 簇约 3.1 °C/W（翻转时 +2.7 °C / 0.85 W），P 簇约 0.4 °C/W，GPU 约 0.46 °C/W。选择性最高的是 E 簇，但绝对值上 GPU 负载 +11.5 °C、P 簇满载 +9 °C，都远大于 E 簇自己造成的 +2.7 °C |
| P 簇旁的 die 传感器 | `TPD0/5/7/X`（偏 P 簇 1）、`TPD1/3/4/6/8/A–E`（偏 P 簇 0） | 无占位值，GPU 影响小（+1.4～+2.2 °C），可作为没有读数时的旁证 |

- **又一个名字陷阱**：`Tp1*`、`Tp2*` 的前缀和 CPU 键一样，但实测更像 SoC/GPU 区域。按名字归簇会让「P 簇最高温」在 GPU 负载时虚高 15–28 °C。
- **Stats 的做法**（2026-10-15 读源码）：
  - CPU 弹窗只显示一个「CPU 温度」，取的是按芯片代际写死的键列表的**平均值**，E 键和 P 键混在一起。M4 的列表是 4 个 `Te*` 加 8 个 `Tp*`，其中 `Te09`、`Te0H`、`Tp0V` 在这台 M4 Pro 上根本不存在（读不到就跳过）。代码不过滤占位值：P 簇断电时，`Tp*` 的 40.0 也会被算进平均。CPU 弹窗里没有按簇或按 E/P 分开的温度。
  - 传感器模块里按代际给每个键起名：M4 把 `Te05`、`Te0S`、`Te09`、`Te0H` 标为「CPU efficiency core 1–4」。其中真实存在的 `Te05`、`Te0S`，正是我们实测的 E 簇弱候选（`Te04/05` 组的 x1、`Te0R/S` 组的 x1）。M2 则把 `Tp1h/1t/1p/1l` 标为 E 核，但我们在 M2 上实测，`Tp1*` 随第二个 P 簇变化，属于标错。
  - 小结：Stats 在 CPU 弹窗里不区分 E 簇；单键标「E 核」只出现在传感器列表中，而且是按名字猜的，没有验证，名字和 M2 的实测矛盾。
- E 簇的情况和 M2 相同：有选择性最高的键，但绝对升幅被 GPU 和 P 簇淹没。这就是 C6 里「E 簇要不要给温度行」的问题，现在两台 P + E 芯片的证据一致。**建议**：E 簇不单独给温度行，只在诊断页显示「E 簇附近」的读数；或者给出，但注明「受 GPU 和 P 簇影响大」。请你选。
- 结论还需要更多工况才能写进芯片档案：这次每种激励只有 1–2 轮，而 M5 当时做了 3 种独立设计。§9.5 列出了要补的部分。

证据：`skeptic-thermal-power/m4out/{etoggle,ptoggle,gpu}_m4.csv`、`m4_attrib2.py` 与 `m4_attrib2.txt`、`m4_sentinel.py` 与 `m4_sentinel.txt`、`thermal-power/smc_enum_m4.txt`。

### 9.4 SMC 读取开销

- 一次批读 297 个键（全部 `T*` 加功耗键）：线程 CPU 中位数约 6.5 ms，墙钟 60–75 ms（p90 约 186 ms）。读取是阻塞的，必须放在采样线程，不能放在 MainActor（D03）。
- 产品只读归簇后的最小集合（约 40 个温度键加 6 个功耗键），按每键的单价估算约 1 ms CPU、10 ms 墙钟。具体数值在实现阶段用 `sk_cost` 在两台机器上实测。

### 9.5 还没做的

- 三元组在 M4 上的显示口径：找出 SMC 自己的 CPU 聚合键（M2 是 `TCMb`），核对它等于哪个变体的最大值。
- P 簇归簇的独立复核：换一种激励再做一次，例如 1×UI 加 E 簇满载，看单线程固定在哪个 P 簇；把相关系数在两轮里的稳定性写进芯片档案的置信度。
- `make measure` 和 SysInfo app 本体还没在 M4 上运行过（M0 在对照机上只跑过 CLI）。上下布局的菜单栏 item 要在两台机器上截图自查。
- 热状态离开 nominal 的迁移：60 s 以内的负载在两台机器上都没能触发。
