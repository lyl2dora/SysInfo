# 应用活动模块验收报告

> 日期：2026-10-17。范围：D67–D70（分支 `module/app-activity`）。补测、规格与偏离记录见 `docs/design/app-activity.md`。

## 结论

- D67–D70 列的内容全部完成：
  - 数据：coalition 全表（CPU、累计 CPU 时间、内存、功率、GPU、ANE、磁盘读写、唤醒、pageins、perflevel0、成员数）；电源断言（合并重复、代他人持有、按 coalition 归到应用）；
  - 界面：独立的应用活动窗口（时间段：现在 / 1 小时 / 今天 / 7 天 / 30 天；分类：全部 / App / 后台与系统 / 阻止睡眠；搜索；可排序、可隐藏的列；应用详情），面板顶栏按钮，各 Top N 底部「在应用活动中查看全部」，合并模式总览的「最耗能的应用」卡片（D70），设置的「应用活动」页；
  - 历史：`app_minute` 扩列 + 每分钟「各列前 10 并集」+「其余合计」（schema 3，D68）；电源断言的开始 / 结束区间（D69）；导出加新列与 `assertions.csv`；
  - CLI：`apps`（现在 / 历史时段）、`assertions`（含 `--watch`）。
- 新增一个私有符号 `IOPMAssertionNotify`（`CSysPrivate/pm.c`，dlsym，带自检；私有层版本 2）。
- 出厂默认与 CPU 面板的开销仍在 D19 预算内；应用活动窗口打开时约 2.2% 单核（两台一致，与 CPU 面板相当，不属于出厂默认）（§2）。
- 请你验收时留意三处：
  - **CPU 模块的 coalition 自检 S4 修了一个误判**（偏离记录第 1 条）：以前它在 M5 上常判为不过，CPU Top N 的能耗列被隐藏，历史库的每应用能耗记成空值。修复后两台 60/60。今天之前的每应用能耗多数是空值，历史时段里按「只计已知部分」显示并标「*」。
  - 表格用 AppKit `NSTableView`，没用 SwiftUI `Table`：后者在窗口打开时要约 5.5% 单核（§2）。
  - 时间段放在工具栏，侧栏只放分类（偏离记录第 2 条）。

## 2. 开销（`docs/perf/app-activity.md`，D40 口径）

| 档位 | M5 | M4 |
|---|---|---|
| 出厂默认（五个 widget，面板关闭；历史现在按各列解析身份、事件驱动记录断言） | 0.46%（第一次 0.38%） | 0.18% |
| 面板打开（CPU tab，Top N 5 行，新增底部入口） | 1.90%（第一次 2.07%） | 1.91% |
| 应用活动窗口打开在「现在」（全表每 2 s） | 2.18% | 2.26% |

- 预算：出厂默认 < 0.5%，面板打开 < 2%。两台都在预算内。窗口不是出厂默认，设置里标了整窗实测开销（D19）。
- 窗口的开销历程（M5）：SwiftUI `Table` 5.9% → 缓存行与合计 5.1% → 换成 `NSTableView` + `reloadData()` 5.5% → 原地更新可见单元格 2.3% → 排序键整数比较 2.2%。`sample` 显示前几版的时间几乎全在表格的行视图重建上（SwiftUI 的 NSHostingView 注销 KVO、`reloadData` 丢掉全部可见行）；扫描本身只占约 0.5%，与补测（§1.4）一致。

## 5. 需要你亲手验收的部分

- 从面板顶栏、存储与 GPU 的 Top N 底部打开窗口（CPU、内存、总览已由 §4 点过），确认排序列分别是写、GPU。
- 表格：拖动列顺序与宽度，退出 app 重开窗口后保持（§4 只验了排序与列显示）。
- 右键一行，实际点一次「结束…」（确认框里应写着被右键的应用名，按住 ⌥ 默认强制）。
- 「现在」档选中一行后，几秒内行位置变化时选中行保持可见。
- 切到「1 小时 / 今天 / 7 天」：已退出的应用出现，「阻止睡眠」分类里有虚拟机等；关掉设置里的「记录每应用数据与电源断言」后提示「没有记录」，总览卡片消失。
- 开一次 `caffeinate -d -t 30`：窗口「阻止睡眠」分类出现 caffeinate；30 s 后在「1 小时」档能看到这段区间。
