# 桌面小组件模块验收报告

> 日期：2026-10-21。范围：D87、D90、D91（分支 `module/widgets`，已合入 `main` 到 D93）。能力边界与探针结果见 `widgets-boundary.md`，规格与进度见 `widgets.md`，开销见 `docs/perf/widgets.md`。

## 结论（待用户验收）

- D90、D91 列的内容已完成：
  - 扩展 `SysInfoWidgets`（沙盒，只链接 SysModel，碰不到私有层）：一个「总览」组件，小 / 中 / 大 / 超大竖版四种尺寸，内容按 WS1 固定（`StaticConfiguration`，WS2）；
  - 主进程写快照（v2，组容器 `widget-snapshot.json`，原子写入），只在有组件放置时登记后台需求、写文件、刷新组件；
  - 组件上的刷新按钮：`RefreshWidgetIntent` 在主进程执行，现采一次再写；
  - SysInfo 没在运行时保留最后的数据并变暗，注明「未运行」与时间（WS3）；正常退出时立即写一份 `appRunning = false`；
  - 设置新开侧栏页「桌面小组件」（刷新节奏 5 / 1 分钟并标注开销、已放置的组件、最近写入时间、放置说明，WS4）；隐私页「数据存放」加组容器一行（W6）；
  - 构建与发布：`check-private-imports.sh` 扫描 `Widgets/`；`build-release.sh` 检查嵌入的 `.appex` 存在并一起签名、核对其 entitlements；`stop-dev.sh` 一并结束 Debug 扩展；`remote-app.sh` 同步扩展目录到对照机。
- 两台机器的扩展侧验证都通过（§1）；出厂默认与面板两档在 M4 复测通过预算（§2）。
- 探针清理：probe B 已停掉并注销；桌面上的两个探针组件（SysInfo Probe Dev / Rel）用户已于 2026-10-21 手动删掉。本机两个探针的组容器还在（受 TCC 保护，没从终端删），不影响正式组件。
- 偏离规格 7 处，均为细节，见 §3。
- 验收中需要用户确认或补测的项目见 §4；2026-10-21 验收中发现并修复的问题见 §6。

## 3. 偏离规格

1. **「想要数据」标记每 30 s 查一次**（规格 §4.1 写的是随 5 分钟的配置检查顺便看）：只是一次文件读取，换来刚放上组件 30 s 内就出数据。
2. **启动后等第一批样本再写**（最多 10 s）：否则第一份快照会把还没采到的项写成不可用（9c4a9d7）。
3. **当前值的陈旧阈值是「节奏 + 30 s」**（规格 §4.2 写的是「比节奏还旧」）：留出轮询粒度的余量，避免恰好在边界上的样本被误判。
4. **曲线退回内存缓冲的条件放宽为「历史库没有数据」**（规格 §4.3 写的是历史记录关闭时）：历史开着但刚启动、库里还没有这一项时也能画出最近 15 分钟（1 分钟一个点），标「15 分钟」；「历史记录已关闭」只标在所属模块历史关着的那条曲线上（§6 第 3 条）。
5. **曲线点数不足两个时显示「暂无数据」**：`--factory-defaults` 用临时历史库，每次启动头 5–10 分钟都是这样，属预期。
6. **测量副本改用 `.dev.measure` 标识**（558fc70）：否则会和桌面上 Debug 版的扩展抢 LaunchServices 登记（probe A：同一 bundle ID 只认一份）。
7. **启动时等每一项的第一个样本**（原来只等 CPU 占用）：先查放置情况、登记需求再等，最多 10 s（§6 第 1 条）。

## 4. 待用户验收与已知问题

需要用户点按确认（D18：真实点击由用户验收）：

1. 放置与删除：放置已验证（2026-10-21，设置页列表正确）；还剩删掉全部组件后列表变为「没有」、不再写快照。
2. ~~历史关闭时的曲线降级~~：2026-10-21 Claude 关掉 `.dev` 的 CPU 历史后截图验证（发现的问题见 §6 第 3 条，已修），只有 CPU 曲线标「15 分钟（历史记录已关闭）」，其余三条仍是 24 小时；验完已恢复。
3. ~~锁屏后解锁~~：2026-10-21 用 `pmset displaysleepnow` 锁屏 01:07:16–01:12:25（本机显示器睡眠即锁定）。锁屏期间 01:10:23 照常写快照，chronod「Reload success」；解锁后组件显示 2 分钟前的数据，在节奏之内。补上了边界文档 §5 没测到的「锁屏时 chronod 是否刷新」：会。
4. ~~Debug 与 Release 并存~~：2026-10-21 经用户同意在本机运行 Release（worktree 构建，新建了日用版偏好域），用户放了一个 Release 小号。两版菜单栏的盘温各连拍 6–8 帧都没有「—」（D93）；Release 组件只显示 Release 写的快照；结束 Release 后只有它的组件变暗（「未运行 · 1 分钟 4 秒」），chronod 只刷新 `zone.lyl.sysinfo.widgets`，Debug 的四个不受影响。验收中发现的补写问题见 §6 第 4 条。

已知问题（不阻塞验收，记下待观察）：

1. **app 放在 `/tmp` 下时刷新按钮无效**：linkd 给 App Intents 建索引时找不到 app（-10814）。拷到 `~/Applications` 后正常；正式版装在 `/Applications` 不受影响。从「下载」直接打开、被 App Translocation 挪到临时路径运行时可能也受影响，未验证。
2. **主进程没在运行时点刷新**：`.main` 的 intent 会不会拉起 SysInfo 还没专门测过（边界文档 §3）。
3. **一次被系统重新拉起**：M4 上结束 `/tmp` 下的实例后，launchd 以「launch job demand」立即重新拉起了它，原因未查明，之后两次没复现。如果复现，要查是不是 App Intents 的连接导致。
4. **对照机清场缺口**：扩展的沙盒容器 `~/Library/Containers/<app>.widgets`（以及 `.measure.widgets`、`.probe.widgets`）不在 `remote-app.sh` 的痕迹清单里，M4 上三个都还在（D39）。

## 6. 验收中发现并修复的问题（2026-10-21）

1. **重启后第一份快照的启动盘是「—」，最多 5 分钟**（本机只有一个实例，没有 SMART 抢占）。根因在存储模块：`SMARTCollector.selfTest()` 读全部盘时记下了读取时间，但自检读数不进 MetricStore；于是第一次采样把非焦点盘（菜单栏盘温绑定的不是它的盘）当作 55 s 内刚读过而跳过。本机菜单栏盘温绑定外置盘，启动盘正是非焦点盘。
   - 修复：自检结束时清掉读取时间，下一次采样照常读全部盘（启动、唤醒等复检时每盘多读一次，约 1 ms）。这同样影响 `main`：非焦点盘在启动后约 1 分钟里没有样本（历史第一分钟缺这些盘）。
   - 小组件写入器同时改为先登记需求、再等每一项的第一个样本（§3 第 7 条）。修复后重启，第一份快照约 2 s 写出，启动盘 72 °C。
   - M4 上 10-20 看到的「—」，SMART 抢占（D93）与这一条可能都有份。
2. **设置页已放置的尺寸顺序不固定**（`currentConfigurations` 的顺序）：改为按小、中、大、超大竖版排列。
3. **只关一个模块的历史，所有曲线都被标成「已关闭」，而且画乱了**：标题与横轴看的是一个全局开关（CPU、功耗、内存三项历史任一关闭就算关），曲线数据却按项从历史库取（库里留着关之前的数据，功耗历史也还开着），24 h 的点画在 15 分钟的横轴上，图表不裁剪，越界的线画到了隔壁的图上。
   - 修复：快照每项带 `curveSource`（`history` 24 h / `historyOff` 该模块历史关着 / `recent` 历史开着但库里还没有，后两种是内存里最近 15 分钟），每项看自己模块的开关（CPU 占用 → CPU，整机功率与 SoC 热点 → 功耗与散热，内存 → 内存）；历史关着时不读库；去掉快照里全局的 `historyEnabled`（v2 没发布过，不升版本）。图表加 `clipped()`。切换这几项历史开关后立刻重写快照，不等 5 分钟。
   - 原来规格 §3 偏离第 4 条里「历史开着但刚启动」的情况，现在标「15 分钟」，不再写「已关闭」。
4. **新放上的组件可能显示一份十几分钟前的快照，最多等 5 分钟才更新**：Release 刚启动时写过一份（图库预览留下的「想要数据」标记触发），用户 10 分钟后放上组件，扩展看快照没到「陈旧」（3 个节奏）就不留标记，主进程要等下一次 5 分钟的放置检查。
   - 修复：扩展在快照比一个写入周期加 60 s 还旧（或主 app 已退出）时就留标记，主进程 30 s 内补写。正常运行时每次刷新都紧跟在写入之后，不会多留标记。新增 `WidgetSnapshot.wantsRefresh(at:)` 与单测。
5. **开发陷阱**：同一 bundle ID 有好几份 Debug 构建登记过时，chronod 会记住组件放置时的那份扩展配置。把那份注销后，扩展一启动就因「Invalid bundle record for current process」崩溃，chronod 一小时后才重试。处理办法是在原路径重新构建、重新登记（或删掉组件重新放）。验收用的 Debug 版因此改为构建到主检出的 `build/DerivedData`。
