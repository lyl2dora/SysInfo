# 功耗与散热模块能力边界（讨论稿）

> 日期：2026-10-15 · 状态：**讨论稿，不是最终设计** · 分支：`module/power-thermal`
> 只想拍板的话，直接看 §6 的 8 个问题（PT1–PT8）。定下来之后，结论追加为新的 D 条目，再另写本模块的实现规格。

## 1. 目的与口径

按 D14，本模块开工前先定能力边界，同时处理启动清单里触发时机已到的待定项：K35（CPU 实时功耗是否按 PMGR 系数校准）、K36（30 分钟批次数据怎么展示），以及 K40、K41 中与本模块有关的部分。D29 划给本模块的内容是：

- SoC 热点、完整传感器目录、风扇读数；
- PMGR 30 分钟批次与分部件明细（K36）；
- 整机、SoC、GPU、DRAM 功耗；
- 按 PMGR 系数校准（K35）；
- 是否给没有专用轨的芯片估算 CPU 功耗。

已在 CPU 模块里的内容不再重复：CPU 按簇实时功耗（D29）、CPU 温度与热状态徽标（D33、D36、D37）、SMC 只读层、IOReport hub、芯片档案、自检框架、历史库（D30）。

依据是 2026-10-15 在两台目标机上同时做的两轮实测：

- 本机 Mac mini Mac17,16，M5 Pro，macOS 27.0.1（26A434）；
- 对照机 Mac mini Mac16,11，M4 Pro，macOS 27.0.1（26A434）。

做法：
- 只读记录器 `ptlog` 每秒记录一次：首字母为 P/T/F/V/I/R 的全部 `flt` 类 SMC 键、Energy Model 全组（AGX `GPU Energy` 实时值，以及 PMGR 通道的变化快照）、`PowerTelemetryData` 累加器、热压力通知值。
- 等到第一个 PMGR 批次边界后，在随后的完整 30 分钟窗口里跑负载，每段 ≤60 s，段间空闲约 2 分钟：
  - 第一轮 7 段：全核 CPU、GPU、DRAM、ANE、HEVC 编码、CPU+GPU、半数核 CPU。
  - 第二轮 5 段：全核 CPU、GPU、CPU+GPU、半数核 CPU、全核 background。第一轮漏记了 R 开头的功耗轨键，第二轮补上。
- 两台机器上都没有运行 Stats。本机开着一个 SysInfo Dev 实例（常驻开销 <0.5%），对窗口对账的影响可以忽略。

口径：
- 「M5」「M4」分别指上面两台机器。
- 「窗口对账」= SMC 键的 1 Hz 积分 ÷ 同一 1800 s 窗口内 PMGR 通道的差分。
- 开销一律指本进程的线程 CPU 时间；「真实节奏」指每 1 s 醒来一次后的第一次调用（D34）。

## 2. 两台机器的能力矩阵

### 2.1 整机与 SoC 功率

| 指标 | 来源 | M5 | M4 | 结论 |
|---|---|---|---|---|
| 整机直流功率 | SMC `PDTR`（= `PD0R`；`PSTR` 就是晚 1 s 的 `PDTR`，两台都是） | 空闲 7.0 W；CPU+GPU 满载约 80 W | 空闲 3.5 W；CPU+GPU 约 50 W，DRAM 压测约 47 W | 两台都可用，1 Hz 实时 |
| 整机 60 s 均值 | `PowerTelemetryData.AccumulatedSystemPowerIn`（mJ，每 60 s 发布一次） | 正常的分钟与 PDTR 一致（中位比值 1.000）；**但满载约 73–78 W 时整分钟丢失，两轮各一次，可复现** | 41 + 53 个分钟全部一致，最高约 50 W，没丢过 | 不能当作唯一的长期能耗来源（§3.1） |
| 墙插功率 | `AccumulatedWallEnergyEstimate` | = 1.035 × DC + 1.62 W | = 1.035 × DC + 1.61 W | 两台公式相同，是**由直流推算的估算值**，不是测量值 |
| SoC 功率（模型） | SMC `PZC0`（= `PZC1`） | 与 PMGR 顶层通道合计之比 0.997 / 0.998 | 1.060 / 1.040 | 可用。M4 偏高 4–6%：M4 的 PMGR 没有 FAB 通道，`PZC0` 可能计入了它 |
| SoC 功率（实测输入） | SMC `PHPC` | 与 PMGR 合计之比 1.12 / 1.19；比 `PZC0` 空闲时高 1.6 W，重载时反而低 1.6 W | 1.13 / 1.19；空闲时高 0.5 W，重载时高 4–5 W | 和 `PZC0` 不是固定偏移。两台的差值随负载变化，而且方向不同 |

第一份清单里「M4 空闲时 `PHPC` 低于 `PZC0`」的疑问已经查清：那是单次读数加上约 1 s 相位差造成的。窗口积分里 `PHPC` 在两台机器上都比 `PZC0` 高 12–19%。

### 2.2 分部件实时功率

| 部件 | 来源 | M5 | M4 | 结论 |
|---|---|---|---|---|
| GPU | AGX `GPU Energy`（nJ，≥10 Hz） | 与 PMGR GPU0 之比 1.002 / 1.001 | 与 PMGR GPU 之比 0.963 / 0.964 | **首选**。两台都和 Apple 的模型一致，误差在 4% 以内 |
| GPU（备选） | SMC GPU 轨：M5 `RP05+RP08`，M4 `RP07+RP0b+RP0c` | 0.995 | **1.385**（GPU 段 24.1 W，同期 AGX 18.7 W） | M4 的轨还包含了 GPU 以外的东西，不能当 GPU 功率用 |
| DRAM | SMC `PZD1` | 与 PMGR DRAM0 之比 1.000 / 1.000 | 与 PMGR DRAM 之比 1.000 / 1.000 | 可用。只含 DRAM 本身，不含内存控制器（AMCC、DCS） |
| CPU | SMC 专用轨（CPU 模块已接入） | 见 §2.4 | 见 §2.4 | — |
| ANE、媒体引擎、AMCC、DCS、FAB 等 | 只有 PMGR 30 分钟批次 | ANE0 236 J / 30 min（第一轮含 60 s ANE 压测） | ANE 197 J | 没有实时来源（§2.3） |

GPU 负载段里的一个现象：CPU+GPU 同时满载时，M4 的 GPU 功率从 18.7 W 掉到 10.3 W；M5 保持在 20.5–21 W。它不影响数据源的选择，可以作为 GPU 模块的观察点。

### 2.3 PMGR 30 分钟批次（K36）

| 项 | M5 | M4 |
|---|---|---|
| 批次间隔 | 1800.0 s（4 次） | 1800.0 s（4 次） |
| 相位 | 开机 + 1183 s（9 月那次开机是 + 193 s） | 开机 + 1673 s |
| 顶层通道名 | `CPU Energy`、`GPU0`、`DRAM0`、`AMCC0`、`DCS0`、`FAB0`、`ANE0`、`AFR0`、`AVE0`、`DISP0`、`DISPEXT0`、`ISP0`、`MSR0` | `CPU Energy`、`GPU`、`DRAM`、`AMCC`、`DCS`、`ANE`、`AVE`、`AFR`、`DISP`、`DISPEXT`、`ISP`、`MSR`（**没有数字后缀，也没有 FAB**） |
| CPU 细分 | `PCPU`、`MCPU0/1`、`PCPM`、`MCPM0/1`、`PACC_n`… | `PACC0_CPU`、`PACC1_CPU`、`EACC_CPU`（三者之和正好等于 CPU Energy）、`PACCn_CPUm`、`ECPUDTLxx` |
| 读一次整组的开销 | 8.7 ms | 12.6 ms |

- 相位随每次开机变化，两台也不同，再次确认只能按计数器变化检测批次，不能写死时刻。
- 通道名在两颗芯片上不同，需要按芯片档案归一化（例如去掉末尾的 `0`，把 `PACCn_CPU`/`EACC_CPU` 映射到簇）。

### 2.4 CPU 专用轨与 PMGR 的比值（K35）

| | M5 | M4 |
|---|---|---|
| 专用轨合计 ÷ PMGR CPU Energy（第二轮窗口） | **0.817** | **0.927** |
| 按簇 | Super（RP00+RP01）÷（PCPU+PCPM）0.696；M 簇 0 0.851；M 簇 1 0.766 | P 簇 0 ÷ PACC0_CPU 0.930；P 簇 1 0.908；E 簇 1.240 |
| 9 月调研的同口径比值（M5） | 0.955 / 0.954（负载较轻的窗口） | — |

K35 原推荐依据的前提是「两个窗口的比值几乎相同（0.955 / 0.954），偏差是系统性的，可以校准」。这一前提已经不成立：
- 同一台 M5，比值从 0.955 掉到 0.817；
- 按簇看在 0.70 到 0.85 之间波动；
- M4 的值又不一样。

比值取决于负载的组成（重载时 Super 簇偏低最多），任何固定系数 k 都会在另一种负载下把数字算错。M5 的簇级 PMGR 通道之间可能有重叠，所以按簇的比值只作参考；合计比值不受这个问题影响。

### 2.5 温度：SoC 热点与传感器目录

**SoC 最热点**。各负载段末 10 s 的均值（°C）：

| 段 | M5 `TCMb` | M4 `TCMz` | M4 `TCMb` |
|---|---|---|---|
| 空闲 | 50.4 | 47.4 | 44.6 |
| 全核 CPU | 89.7 | 75.8 | 72.3 |
| GPU | 81.4 | 82.7 | 82.7 |
| DRAM | 90.3 | 98.1 | 89.8 |
| ANE | 77.7 | 72.1 | 71.5 |
| HEVC | 58.2 | 54.9 | 52.1 |
| CPU+GPU | **108.3** | **100.1** | 97.7 |
| 半数核 CPU | 91.0 | 83.0 | 78.4 |

- 「全体有效温度键的逐秒最大值」由哪个键代表：
  - M5 是 `TCMb`：与逐秒最大值的差中位数 0，p95 0.39 °C，最大 9.0 °C；`TVD0` 接近。
  - M4 是 `TCMz`：差中位数 0，p95 0；`TCMb` 平均低 2.8 °C。
  两台芯片用的键不同，所以要由芯片档案或运行时的「聚合键检测」来定（CPU 模块 §7.3 第 4 步已有这个检测）。
- M4 的 `TCMz` 在 CPU 区全部断电时会停在一个旧值上：所有 `Tp0*` 都是占位值的时段里，有 43–49% 的秒和上一秒完全相同；其余时段只有 4–6%。偏差约 +2.8 °C，量级不大，但这时的读数是陈旧的。
- `TPDX`、`TRDX`、`TTDX` 是各自分组的最大值，比最热点平均低 3–10 °C，不适合当「最热」。

**传感器目录**：

| | M5 | M4 |
|---|---|---|
| `flt` 温度键 / 其中有变化的 | 234 / 218 | 270 / 256 |
| 电压 V / 电流 I / 功率 P | 40 / 50 / 64 | 43 / 45 / 57 |
| 占位值（断电时的固定读数） | 几乎没有：只有恒为 0 的 `Tz1*`、`T?DF`；另有不是温度的 `TNSz=1024`、`TNLc=4`、`TVMD=1` | **约 170 个键有**，而且取值各不相同：−4.0、0.0、1.5、2.2、2.3、2.4、8.2、40.0……例如 `Tp1n` 断电时读 40.0，上电过渡时读 1.5 |

M4 的占位值比 D33 记录的（`Tp*` 40.0、`Tg*` −4.0/0.0）更多样，按固定值列表识别会漏，需要「芯片档案 + 运行时检测长时间精确不变的值」两层识别。还要注意不能误伤聚合键：M4 的 `TCMz` 也会长时间精确不变（上一条）。

按负载响应可以确认的分组（两台一致）：
- `Tg*` 随 GPU 负载升高（M5 +26 °C；M4 上电后达 75–94 °C）；
- `Ta*` 随 ANE 负载升高（M5 +16–17 °C；M4 上电后约 70 °C）；
- CPU 区键见 D33、D36。

其余大部分键无法如实命名。

### 2.6 风扇

| | M5 | M4 |
|---|---|---|
| 风扇数 `FNum` | 1 | 1 |
| 范围 `F0Mn`–`F0Mx` | 1000–4900 RPM | 1000–4900 RPM |
| 实测 | 只有 CPU+GPU 段（`TCMb` 约 108 °C）升到 **2291 / 2577 RPM**，其他段都停在 1000 | 全程 998–1002，**100 °C 时也没升** |
| 键 | `F0Ac`、`F0Tg`、`F0Mn`、`F0Mx`、`F0Dc`；模式键 **`F0md`** | 同左；模式键 **`F0Md`**（大写 M） |

模式键的大小写在两颗芯片上不同，和温度键一样只能在运行时发现。Mac mini 的风扇在 60 s 负载里基本不动，所以风扇读数主要用于确认「风扇在转、处于哪个档」，信息量有限。

### 2.7 热压力

两台机器在所有负载段（包括 108 °C 的 CPU+GPU 段）里，`com.apple.system.thermalpressurelevel` 都停在 0（nominal）。60 s 以内的负载触发不了状态变化，这和 CPU 模块 §9.5 的结论一致。

### 2.8 开销（真实节奏，线程 CPU 中位数）

| 读取 | M5 | M4 |
|---|---|---|
| SMC 3 键（PDTR + 热点 + 风扇） | 0.22 ms | 0.35 ms |
| SMC 15 键（面板的功耗分解与散热） | 0.61 ms | 1.23 ms |
| AGX `GPU Energy` 单通道订阅 | 1.38 ms | 1.77 ms |
| `PowerTelemetryData` | 0.15 ms | 0.23 ms |
| Energy Model 整组（检测批次） | 8.7 ms | 12.6 ms |
| 紧循环 SMC 每键 | 22 µs | 67 µs |

M4 读 SMC 每键约是 M5 的 3 倍，可能和调度到能效核有关（D40）。

## 3. 与调研报告、决策档不同的发现

### 3.1 `PowerTelemetryData` 累加器在高负载下会丢整分钟（影响 D08）
- 现象：M5 在 CPU+GPU 段（PDTR 73–78 W）里，有一个 60 s 发布周期的 `SystemPowerInAccumulatorCount` 只加了 1，这一分钟的能量（约 4.7 kJ）没有记入累加器，以后也没有补回。两轮各出现一次（19:42:05、20:33:05），可复现。
- 第一轮窗口里累加器合计只有 PDTR 积分的 0.859。M4 最高约 50 W，没出现过。49 W 的 DRAM 段在 M5 上也没丢，触发门槛在 49–73 W 之间。
- D08 写的是「整机的长期能耗可以直接取 `PowerTelemetryData` 的累加器」。照这样做，重载时段的能耗会少算，而且没有任何标记。

### 3.2 K35 的前提不成立
CPU 专用轨与 PMGR 的比值随负载组成变化（§2.4），不是可以用一个系数校准的系统偏差。

### 3.3 M4 的 GPU 轨不是 GPU 功率
M4 的 `RP07+RP0b+RP0c` 比 PMGR GPU 和 AGX 高 38%。CPU 模块 §9.2 写的「`RP07` + `RP0b` 为 GPU」只能理解为「GPU 负载时升高的轨」。GPU 功率统一用 AGX。

### 3.4 墙插功率是公式，不是测量
两台机器都满足 `墙插 = 1.035 × DC + 1.6 W`，两颗芯片的系数相同，不随负载组成变化。调研报告 §1.6 写的「DC/墙插比 0.86–0.90」只是这条公式在中等负载下的结果。

### 3.5 其他
- `PHPC` 与 `PZC0` 的关系随负载和芯片变化（§2.1），不能用一个固定偏移互推。
- PMGR 通道名和簇细分的命名在 M5、M4 上不同（§2.3）。
- 风扇模式键大小写不同（§2.6）。
- M4 的温度占位值远比 D33 记录的多样（§2.5）。

## 4. 建议的模块边界

### 4.1 纳入本模块
- **功率**：
  - 整机直流功率 `PDTR`；
  - SoC 功率 `PZC0`，`PHPC` 只进诊断页；
  - GPU 实时功率（AGX）；
  - DRAM 功率 `PZD1`；
  - CPU 功率复用 CPU 模块的专用轨读数。
  - 墙插功率是否显示、显示在哪里，见 PT5。
- **最近 30 分钟**：PMGR 批次的分部件明细（K36），包括 ANE、媒体引擎、内存控制器、fabric 等。
- **长期能耗**：按小时、天累计 kWh（PT5）。
- **散热**：SoC 最热点、风扇（转速、目标转速、占范围百分比、模式）、热压力状态与变化记录。
- **传感器目录**：只放诊断页（PT6）。
- **共享数据源**：AGX `GPU Energy` 订阅和 PMGR 批次检测在本模块建立，GPU 与加速器模块以后直接复用。

### 4.2 划给其他模块
- GPU 与加速器：GPU 利用率、ANE 是否活跃、媒体引擎活动强度，以及 ANE 准实时估算（coalition slot 39 对账）。本模块只提供功率数据源。
- 应用活动：每应用能耗列。
- P1「电源设备」：UPS、配件电量。
- 电源断言（谁在阻止睡眠）、低功耗模式：见 PT1。

### 4.3 不做
- 用固定或动态系数校准 CPU 功耗（PT2）。
- 给没有专用轨的芯片估算 CPU 功耗：M2 已经不是目标设备（D28），继续显示「不可用」（D29）。
- 用 SMC GPU 轨当 GPU 功率（§3.3）。
- 把 PMGR 批次数据画进实时曲线（K36 的选项 C）。
- HID 温度、HID 电流电压（D29、调研报告 §1.6）。
- 风扇控制：D04 预留，不在 v1。

## 5. 产品方案草案

以下按 §6 各题的推荐写成，你改选后相应调整。

### 5.1 菜单栏（D38：一项一个 widget）
本模块提供的 widget：

| widget | 数值 | 出厂默认 |
|---|---|---|
| 整机功率 | `PDTR`，τ ≈ 2 s 平滑，「48 W」 | 开 |
| SoC 最热点 | 「92°」 | 关 |
| SoC 功率 | `PZC0` | 关 |
| GPU 功率 | AGX | 关 |
| 风扇 | 「1000」RPM | 关（有风扇时才出现） |

样式沿用 D38、D41、D43：上下布局、每个 widget 自选颜色、宽度按最坏情况固定。功率按「188 W」的宽度算，温度按「110°」。

### 5.2 面板（功耗与散热 tab）
从上到下：
1. **概览**：大号整机功率，右侧三个小值：SoC 功率、SoC 最热点、风扇转速（无风扇时不显示）。
2. **历史图**：整机功率，可叠加 SoC 功率；跨度同 CPU（2 分、15 分、1 时、24 时、7 天）。
3. **功率分解（实时）**：CPU（专用轨，按簇可展开，链接到 CPU tab）、GPU、DRAM 各一行，SoC 合计单独一行。是否显示「其他」见 PT4。
4. **最近 30 分钟**（K36）：
   - 卡片标题写明窗口起止时间和「X 分钟前更新」；
   - 列出 PMGR 分部件的平均功率，包括 CPU、GPU、ANE、媒体引擎（AVE）、内存控制器（AMCC+DCS）、DRAM、fabric、显示、ISP 等；
   - 注明「Apple 功耗模型口径，每 30 分钟更新一次」；
   - 开机后第一个批次到来前，显示「等待首个批次（约 N 分钟）」。
5. **散热**：SoC 最热点、风扇（转速 / 目标 / 范围百分比 / 自动或强制）、热压力徽标和最近的状态变化。
6. **能耗**：今天、昨天、近 7 天的 kWh（PT5）。

面板内的采样只在本 tab 可见时进行：功率、温度、风扇 1 s；30 分钟卡片在可见时每 60 s 检查一次批次。

### 5.3 设置页（按 D41 分节：菜单栏、采集、面板、历史）
- **菜单栏**：上表各 widget 的开关；打开后就地展开该 widget 的配置。
- **采集**：本模块常驻间隔覆盖；面板内各项的刷新间隔。
- **面板**：功率分解是否显示「其他」（如 PT4 选 B）、墙插功率是否显示（PT5）。
- **历史**：是否记录本模块历史、是否记录能耗。

### 5.4 历史
- 分钟级记录：整机功率（均值、峰值）、SoC 功率、GPU 功率、DRAM 功率、SoC 最热点（均值、峰值）、风扇转速、热压力。
- 能耗：每分钟的焦耳数，来自 PDTR 积分（PT5），小时级永久保留，可以换算成按天的 kWh。
- 面板关闭时由 background 层继续：
  - PDTR 每 1 s。菜单栏 item 开着时复用 1 s tick，不开时也需要 1 s 才积分准确，开销见 §5.6；
  - 温度和风扇每 10 s；
  - PMGR 批次每 60 s 检查一次，变化时存一份快照，保证打开面板时能立刻显示最近一批。

### 5.5 诊断页
- `PHPC`、`PPSR`、`PMVC` 等原始功率键；
- 传感器目录（PT6）；
- PMGR 全部通道的最近一批数据；
- 热点键的来源（芯片档案或聚合键检测）；
- 占位值识别结果；
- 遥测累加器与 PDTR 的逐分钟对账，丢失的分钟标红。

### 5.6 出厂默认配置的开销估算（D19、D40）
- **常驻**：整机功率 widget，以及 background 历史（PDTR 1 s、温度和风扇 10 s、批次检测 60 s）：
  - 每秒约 0.1–0.2 ms，即 0.01–0.02% 单核；
  - 加上批次检测摊到每秒的约 0.15–0.21 ms，合计约 0.03–0.04%。
  - CPU 模块的常驻部分不变。合计仍远低于 0.5%。
- **面板打开**（本 tab 可见）：SMC 15 键 + AGX 单通道，每秒约 2–3 ms，即 0.2–0.3% 单核，与 CPU tab 不会同时可见。
- 以上是按探针单价估算的，实现后用 `make measure` 在两台机器上实测。

## 6. 需要你拍板的问题

### PT1 范围：哪些内容放进本模块？
- **A（推荐）**：§4.1 的全部内容。AGX GPU 功率在本模块建立，GPU 模块以后复用。低功耗模式只做一个徽标，放在散热区（公开 API，几乎零开销）。电源断言（谁在阻止睡眠）不做，留到「应用活动」或 P1 再议。
- **B**：A 再加电源断言列表。
- **C**：GPU 功率留给 GPU 与加速器模块；本模块只做整机、SoC、DRAM。
- 理由：GPU 功率是 SoC 功率分解里最大的一块，没有它分解就不完整；数据源只建一次，两个模块共用。电源断言和散热、功耗关系不大，放进来会让 tab 变杂。

### PT2 CPU 功耗是否按 PMGR 系数校准？（K35）
- **A（推荐）**：不校准，实时值一律显示 SMC 专用轨的原值。「最近 30 分钟」卡片里并排给出 PMGR 口径的 CPU 平均功率。系数只在诊断页作为观察值，不参与显示和自检。
- **B**：乘固定系数 k。
- **C**：每来一批 PMGR 数据就动态更新 k。
- 理由：比值随负载组成在 0.70–0.93 之间波动，两颗芯片也不同（§2.4），固定 k 必然在另一种负载下出错；动态 k 只是把 30 分钟前的负载组成套到现在。专用轨是电源轨上的实际读数，PMGR 是模型，两者口径不同，各自标明即可。

### PT3 30 分钟批次怎么展示？（K36）
- **A（推荐）**：单独一张「最近 30 分钟」卡片（§5.2 第 4 项），写明窗口和更新时间，注明模型口径。实时区不显示 ANE 和媒体引擎的瓦数。ANE 准实时估算（coalition slot 39）留给 GPU 与加速器模块，对账通过后再上线。
- **B**：A 再加实时区的「ANE 功耗（估算）」，本模块就做 slot 39 对账。
- **C**：不展示批次数据，只在后台使用。
- 理由：这是 K36 原推荐的第一步。ANE 是否活跃、媒体引擎活动强度属于 GPU 与加速器模块的内容，在那里做对账更自然。

### PT4 实时功率分解里要不要「其他」一行？
- **A（推荐）**：不要。CPU、GPU、DRAM 各一行，SoC 合计单独一行，不画堆叠图，不做相减。
- **B**：加「其他 = SoC 合计 − CPU − GPU − DRAM」，钳到 ≥0，标「推算」。
- 理由：
  - SoC 合计（`PZC0`）、GPU（AGX）、DRAM（`PZD1`）都是模型口径，CPU 却是专用轨的实测。M5 上 CPU 重载时，专用轨比模型低最多约 30%（Super 簇），这部分差额会被算进「其他」，让它在 CPU 负载下虚涨几瓦。
  - M4 的 `PZC0` 本身就比 PMGR 合计高 4–6%。
  - 相减得到的数会让人误以为有个真实的「其他」部件。

### PT5 整机能耗与墙插功率怎么做？（影响 D08）
- **A（推荐）**：
  - 长期能耗由本 app 对 `PDTR` 做 1 Hz 积分，写入历史库。app 没运行的时段，用 `PowerTelemetryData` 累加器的差值补上，标「系统累计，可能偏低」。
  - 墙插功率只在面板概览的次要位置显示，标「估算」；不提供菜单栏 widget。
  - 追加一条 D 条目，修订 D08 中「长期能耗直接取累加器」一句。
- **B**：照 D08 只用累加器。实现最简单，但重载时段会少算，而且没有标记（§3.1）。
- **C**：不做长期能耗，只显示实时功率。
- 理由：PDTR 积分在正常分钟与累加器逐分钟一致，又不会丢重载分钟。代价是必须 1 s 采样，不过 PDTR 单键每秒只要几十微秒（§2.8）。墙插值是 1.035 × DC + 1.6 W 的公式（§3.4），单独做 widget 没有额外信息，标明是估算即可。

### PT6 传感器目录放在哪里、怎么命名？
- **A（推荐）**：只放诊断页。按前缀列出全部原始键：键名、当前值、类型、数据质量（有效 / 占位 / 恒定 / 非温度）。只有经过负载验证的分组才给名字：CPU 簇（D33）、「随 GPU 变化」（`Tg*`）、「随 ANE 变化」（`Ta*`）、SoC 最热点；其余显示原始键名，不猜。
- **B**：像 Stats 那样在面板里放一个带名字的传感器列表。
- **C**：不做传感器目录。
- 理由：两台芯片上只有少数键能按负载响应确认含义，按名字猜的标签已在 M2、M4 上被证伪过（CPU 边界稿 §9.3）。诊断页里保留原始目录，以后排查问题时用得上，而且不会误导。

### PT7 SoC 最热点用哪个键？
- **A（推荐）**：由芯片档案指定一个 SMC 聚合键（M5 `TCMb`，M4 `TCMz`）。档案是由「聚合键检测」，也就是与有效温度键逐秒最大值的吻合度，在实测里生成的。未知芯片先在运行时检测，检测期间显示「—」。M4 上 `TCMz` 停在旧值的问题（约 +2.8 °C），在诊断页注明。
- **B**：自己对芯片档案列出的 20–40 个有效温度键取逐秒最大值，并排除占位值。
- 理由：A 每次只读一个键；B 在 M4 上每秒要多读几十个键，按 67 µs/键约多 2–3 ms CPU，常驻代价是 A 的十几倍。A 与真实最大值的差在两台上 p95 都 ≤0.4 °C。

### PT8 菜单栏 widget 的出厂默认？（K40、K41）
- **A（推荐）**：只默认打开「整机功率」，其余 widget（SoC 最热点、SoC 功率、GPU 功率、风扇）默认关。
- **B**：默认打开「整机功率」和「SoC 最热点」两个（K40 原推荐）。
- 理由：你在 D32 提过多个模块同时显示时菜单栏宽度紧张。整机功率是本模块独有、最常看的数；SoC 最热点在 Mac mini 上平时变化慢（空闲 45–50 °C），而且 CPU 模块已经提供了可选的 CPU 温度 widget。

### 默认采纳、不单独提问的做法（你没有异议就一并采纳）
- 风扇只读（D04）；风扇模式键（`F0md`/`F0Md`）、风扇数在运行时发现。没有风扇的机型不出现风扇行和 widget。
- 热压力只做徽标和变化记录，不参与任何着色（D43）。
- 功率 widget 和面板的功率值做 τ ≈ 2 s 的 EMA 平滑；历史存原始 1 s 值的分钟聚合。
- PMGR 通道名按芯片档案归一化；批次按计数器变化检测；批次快照写进历史库，以便重启后立即显示。
- 占位值识别 = 芯片档案中的值 + 运行时「长时间精确不变」检测，并为聚合键开例外。
- 遥测累加器每 60 s 和 PDTR 积分对账一次，结果进诊断页；连续失配时把「系统累计」补数标为可疑。
